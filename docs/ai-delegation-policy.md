# AI 위임 규칙(서버 적용)

2026-11-09 사용자 결정으로 하위 카드 위임·그룹 문서 지시의 새 대화 CLI·모델·사고 강도를 서버가 정한다.

이전에는 이 규칙이 총괄·문서 루트 AI 대화와 카드 본문에만 있었다. 그래서 규칙이 바뀌면 총괄 AI가 문서 루트 AI들에게 알렸고, 깨어난 AI마다 맡은 카드를 모두 다시 읽어 옛 모델 문구를 고쳤다. 이 때문에 주간 사용량이 급격히 늘었다. 이제 규칙은 한 곳에만 두고, AI 대화에는 전달하지 않는다.

## 규칙 원본과 바꾸는 방법

규칙은 웹 화면의 **계정 메뉴 → AI 위임 규칙**에서 바꾼다. 저장하면 `server/data/_ai-delegation-policy.json`에 기록되고, 서버 재시작 없이 다음 위임부터 적용된다. AI 대화나 카드에는 알리지 않는다.

- 편집자만 열 수 있다(분산 작업 설정과 같은 조건). 로그인한 사람만 저장할 수 있고, AI 연동 토큰으로는 읽거나 바꿀 수 없다. 저장한 사람·시각을 남긴다.
- CLI·모델·사고 강도·권한 모드는 AionUi 에이전트 목록에서 고른다. AionUi에서 확인되지 않는 저장값은 「AionUi에서 확인 안 됨」으로 표시하고 지우지 않는다. 실행 머신에 없는 값은 위임할 때 거절된다.
- 업무 유형·카드 구분(모두·문서 루트·하위 카드)·분석 규모(모두·기본·대규모)의 조합 8개가 모두 정확히 한 행에 맞아야 저장된다. 화면이 빠지거나 겹친 조건을 먼저 알리고, 서버도 같은 기준으로 다시 검증한다.
- 다른 사람이 먼저 저장했으면 덮어쓰지 않고 409(`AI_DELEGATION_POLICY_CONFLICT`)로 거절한다. 화면을 다시 열어 최신 규칙에서 고친다.
- 저장값이 없으면 `server/lib/aiDelegationPolicy.mjs`의 기본 규칙(아래 표, 2026-11-09 결정)을 쓴다. 화면의 「기본값 불러오기」로 되돌릴 수 있다.
- 파일 형식이 깨져 있으면 다른 규칙으로 대신하지 않고 서버 기동을 멈춘다. Claude 계정 정책 파일과 같다.
- 위임할 때는 그 시점의 규칙을 한 번 읽어 그 요청이 끝날 때까지 같은 규칙을 쓴다. 응답 `aiPolicy.revision`은 화면에 표시하는 규칙 버전과 같다.

기본 규칙:

| 행 ID | 업무 유형(`workType`) | 카드 구분 | 분석 규모(`analysisDepth`) | CLI | 모델 | 사고 강도 |
|---|---|---|---|---|---|---|
| `review/any/standard` | `review` | 모두 | `standard` | Claude Code | `opus` | `xhigh` |
| `review/any/deep` | `review` | 모두 | `deep` | Claude Code | `opus` | `max` |
| `other/document-root/any` | `other` | 문서 루트 | 모두 | Claude Code | `opus` | `xhigh` |
| `other/sub-card/standard` | `other` | 하위 | `standard` | Codex CLI | `gpt-6.1-sol` | `xhigh` |
| `other/sub-card/deep` | `other` | 하위 | `deep` | Codex CLI | `gpt-6.1-sol` | `max` |

- 행 ID는 조건(업무 유형/카드 구분/분석 규모)으로 만든다.
- 검수 여부를 먼저 본다. 검수는 하위 카드도 Claude Code·Opus다.
- 조합마다 정확히 한 행만 일치하며, 여러 행의 값을 섞지 않는다(`tests/ai-delegation-policy.test.mjs`).
- 문서 루트(계층상 부모가 없는 원본 루트)만 상위 카드다. 하위에 다시 위임하는 중간 카드도 하위 카드다.
- 그룹 문서 지시의 대상은 항상 문서 루트이므로 상위 카드 규칙을 쓴다.
- CLI는 AionUi 에이전트의 `backend`(`claude`·`codex`)로 찾는다. 실행 머신마다 에이전트 ID가 달라도 같은 규칙이 적용된다.
- 권한 모드는 규칙에 없다. 같은 CLI의 요청값이나 대상 카드·상위 대화의 모드를 쓰고, 없으면 화면의 「기본 권한 모드」(기본값 Claude Code `acceptEdits`, Codex CLI `full-access`)를 쓴다. 다른 CLI의 모드는 물려받지 않는다.
- 기술·MCP·작업 디렉토리·Claude 계정은 기존 상속·계정 정책을 그대로 따른다.

## AI가 보내는 값

`mindnprogress_delegate_ai_work`와 `mindnprogress_send_group_document_instruction`은 다음 값을 받는다.

- `workType`(필수): `review`(검수) 또는 `other`(그 밖의 업무).
- `analysisDepth`(선택, 기본 `standard`): 대규모 검수나 복잡한 원인 분석이면 `deep`.
- `aiPolicyOverride`(선택): 사용자가 이번 요청에서 다른 AI 설정을 직접 지정한 경우에만 쓴다. 그 발언을 `evidence`에 적고 `newConversation`의 `agentId`·`modelId`와 함께 보낸다. 카드나 과거 지시에 적힌 설정은 근거가 아니다.

`newConversation`의 `agentId`·`modelId`는 선택 항목이 됐다. 예외 없이 적은 값은 규칙 값으로 바뀌고, 응답 `aiPolicy.adjustments`에 바뀐 항목이 표시된다. AI가 기억한 옛 규칙은 이렇게 위임할 때 그 AI에게만 바로잡히고, 다른 대화는 깨우지 않는다.

`workType`이 없는 하위 위임 HTTP 요청은 이전과 같이 명시값·상속으로 정한다. 그룹 문서 지시는 `validation`이면 검수, 그 밖에는 검수 외·기본 규칙으로 정한다. 도구 정의가 바뀌기 전에 열린 대화의 MCP 연결과 기존 시험이 여기에 해당한다. 새 도구 정의는 `workType`을 필수로 받는다.

## 하위 카드의 담당 대화와 이어가기

2026-11-11 사용자 결정으로 하위 위임도 카드의 담당 대화를 사용한다. 2026-11-14 변경: 담당의 CLI가 규칙과 같으면 모델이 달라도 대화 ID·이력·담당을 유지하고 실행 직전에 모델을 변경한다. CLI가 다를 때는 연결된 후보 중 규칙 모델의 최신 대화를 선택하고, 없을 때만 새 대화를 생성한다. 이미 규칙과 같은 담당은 유지한다.

- 요청한 대화·전략보다 담당과 규칙을 먼저 확인한다. 자동으로 대상이 바뀌면 새 대상의 문맥을 다시 평가하며 이전 대화의 평가 ID·포화 예외를 재사용하지 않는다.
- 일치 후보가 실행 중이면 바쁘다는 응답을 반환하며 다른 대화를 만들지 않는다. 담당을 명시적으로 해제한 카드는 사용자 재선택이 필요하다.
- 즉시 실행과 작업공간 대기열 모두 실제 실행 확인 후 담당을 저장한다. 대기 중 담당이나 CLI가 바뀌면 전달을 중단한다. 같은 CLI의 모델은 접수 당시 규칙으로 맞춘다. CLI 정보가 없는 구형 대기 기록에는 기존 모델 일치 검사를 유지한다. 전송 중 사람이 담당을 바꾸면 그 선택을 보존하고 연결 경고를 남긴다.
- 선택 결과는 `aiPolicy.primaryResolution`과 내구 기록 `delegation.primarySelection`으로 확인한다. 새 대화로 전환한 경우 기존 `aiPolicy.resumeConversion`도 유지한다. 같은 멱등 키의 재시도는 기존 실행을 반환한다.
- 재사용 대화도 실행 직전에 접수 당시 규칙의 모델을 먼저 적용하고, 변경된 모델의 사고 레벨 목록을 다시 조회해 사고 강도를 적용한다. AionCore `runtime/ensure`로 실제 옵션을 확인하고 `config-options`로 변경한 뒤 `runtime-config`의 실제 모델·사고 강도를 대조한다. 확인 실패 시 작업 지시는 보내지 않는다. `runtimePolicyVerification`에 이전 값·확인값·시각을 남기며 카드 대화 목록·작성자 귀속의 모델과 사고 강도도 갱신한다. 모델 변경은 한 번만 요청하며, 변경 후 사고 강도 적용에 실패하면 변경된 모델을 자동으로 되돌리지 않고 위임을 중단한다. 명시적 규칙 예외와 중단된 기존 위임의 복구에는 새 규칙을 강제하지 않는다.
- `runtime/ensure` 직후에는 사고 레벨 목록이 아직 도착하지 않을 수 있다. 목록이 비었거나 모델이 저장된 스냅샷으로만 보이면 0.5초 간격으로 확인하며, 최초 조회부터 준비·변경·실제 값 확인 전체를 최대 30초로 제한한다. 요청마다 시간을 초기화하지 않는다. 준비 시간 초과는 `AI_DELEGATION_POLICY_RUNTIME_READINESS_TIMEOUT`, 준비된 목록에 요청값이 없는 경우는 `AI_DELEGATION_POLICY_RUNTIME_UNSUPPORTED`로 구분한다. 실패한 하위 작업을 자동 재실행하지 않는다.
- 작업공간 대기 접수 후 시작이 거부되면 `reportKind=startup-failure`와 원인 코드를 저장하고 기존 상위 보고 경로로 알린다. 상위가 실행 중이면 유휴 상태를 기다리며, 응답 유실 시 같은 알림 요청의 전달 상태만 확인한다. 전달 확인 후 원 위임은 `failed`, `childStatus=rejected`로 유지하고 `reportStatus=received`로 알림 수신만 구분한다. 수정 이전의 실패 기록을 일괄 재전송하거나 재위임하지 않는다.
- 중단된 같은 위임의 재개(`waiting-child-resume`)와 `aiPolicyOverride`가 있는 요청은 바꾸지 않는다.
- 후보 조회 실패는 후보 없음으로 취급하지 않으며 새 대화를 만들지 않는다.
- 원래 요청한 방식·대화는 `primarySelection.requestedStrategy`·`requestedConversationId`로 남긴다. 이어가기에서 새 대화로 바뀐 경우에는 기존 `aiPolicyResumeConversion`도 남긴다.
- 접수 실패의 재접수 확인은 서버가 바꾼 방식·대화가 아니라 원래 요청을 기준으로 비교한다.
  - 재접수 참조(`retryOfRequestId`)가 있는 위임: 접수 때 같은 업무로 이미 검증했으므로 방식·대화를 비교하지 않는다.
  - 참조 없이 다시 접수한 위임: 전환 기록의 원래 대화로 비교한다.
  - 2026-11-09 운영에서 resume 요청이 문서 버전 충돌로 실패한 뒤 재접수가 새 대화로 바뀌었다. 이때 「후속 접수는 있지만 같은 업무의 재접수인지 확인할 근거가 부족합니다」가 해제되지 않은 결함을 이렇게 고쳤다.

## 그룹 문서 지시의 담당 대화

2026-11-10 사용자 결정으로 그룹 문서 지시는 카드의 `aiPrimaryConversationId`를 담당으로 사용한다. 「AI 대화 선택」 목록의 담당 체크로 변경하며, 기존 카드에 지정값이 없으면 최신 대화를 초기 담당으로 취급한다. 새 보조 대화 연결이나 대화 열기는 기존 담당을 변경하지 않는다.

지시 접수 시 담당의 현재 모델이 위임 규칙과 다르면 다음 순서로 처리한다.

1. 루트 CLI가 달라지면 아래 「루트 카드 CLI 전환 인계」를 우선한다.
2. 같은 CLI이면 현재 담당을 유지한다. 다른 보조 대화에 규칙 모델이 있어도 이동하지 않으며 실행 직전에 현재 대화의 모델·사고 강도를 변경한다.
3. 기존 대화가 없으면 규칙으로 새 대화를 만들고 생성·연결 성공 후 담당으로 저장한다.

규칙과 이미 같은 담당은 유지한다. 같은 CLI의 담당이 실행 중이면 담당을 유지한 채 지시 전달을 대기하며 중복 대화를 만들지 않는다. 후보 조회 실패는 후보 없음으로 취급하지 않는다. CLI 전환 등으로 대상 대화가 변경되면 이전 대화의 평가 ID·포화 예외를 재사용하지 않고 선택한 대화를 새로 평가한다. 담당 변경과 기존 대화에 대한 지시 접수는 함께 저장한다. 대기 중 사람이 담당을 변경하면 해당 지시를 만료시키며 선택을 덮어쓰지 않는다.

실제 선택과 이전 담당·규칙 모델은 `instruction.primaryResolution`과 최초 응답의 `aiPolicy.primaryResolution`에 남는다. 새 대화가 필요한 경우 `aiPolicy.resumeConversion`도 반환한다. 같은 멱등 키 재요청은 기존 지시를 반환하므로 다시 생성하거나 전환하지 않는다.

사용자가 이번에 다른 모델을 직접 지정한 `aiPolicyOverride` 요청에는 자동 모델 교체를 적용하지 않는다. 별도 보조 AI에게 보내려면 `targetConversationRole=auxiliary`와 `aiPolicyOverride.evidence`를 함께 전달하며 담당은 변경하지 않는다. 단순히 최신 보조 대화 ID를 전달하는 것으로 담당이 바뀌지는 않는다. 담당 삭제 시 남은 보조 대화를 자동 지정하지 않으며 사람이 다시 체크한다. 명시적 인계 도구는 후속 대화가 준비되었을 때 담당을 옮긴다.

## 응답

접수한 위임·지시의 응답에는 `aiPolicy`가 붙는다.

- `rule`: 적용한 행 ID. 예외면 `null`이다.
- `cardLevel`: `document-root` 또는 `sub-card`.
- `applied`: 실제로 고른 CLI·모델·사고 강도·모드.
- `adjustments`: 요청값 중 규칙 값으로 바뀐 항목.
- `resumeConversion`: 이어가기를 새 대화로 바꾼 경우의 기록.
- `message`: 위 내용을 알리는 문장.
- `revision`: 규칙 버전(규칙 표의 해시).

규칙의 모델이나 사고 강도가 실행 머신의 AionUi에 없으면 다른 값으로 바꾸지 않는다. 이때는 `AI_DELEGATION_POLICY_UNAVAILABLE`(그룹 지시는 `GROUP_DOCUMENT_INSTRUCTION_POLICY_UNAVAILABLE`, 409)로 거절한다. 입력 값이 잘못되면 `*_POLICY_REQUEST_INVALID`(400)다.

## 적용하지 않는 곳

- 같은 카드의 수동 대화 인계(`start_card_conversation`)는 지정하지 않은 설정을 이전 대화에서 상속한다. 규칙에 따른 루트 CLI 전환 인계는 서버가 고정한 후속 실행 설정을 사용한다.
- Dooray 업무 대응의 AI 설정은 기존 화면 선택과 `aiModelPolicy`를 따른다.

Codex 모델·사고 강도 변경은 AionCore가 동일 `threadId`의 변경 요청 응답과 `thread/settings/updated`의 실제 값을 모두 확인한 뒤 성공을 반환한다. 이미 같은 값인 요청은 변경 통지가 생략되므로 CLI의 시작·재개 응답 또는 앞서 받은 변경 통지의 실제 값과 성공 응답을 확인한다(설치된 Codex 0.167.1 임시 세션 실측). 화면용 선반영 값만으로 성공 처리하지 않는다. Core 확인 대기는 변경당 최대 10초이며 MnP의 전체 30초 제한도 함께 적용한다. 이 확인 처리가 포함된 AionCore 빌드와 MnP를 함께 적용해야 한다.

## 대화 시작 화면의 「AI 위임 모델」

- 대화 시작 화면에는 「AI 위임 모델」 설정이 있었다. 켜면 새 대화의 첫 메시지에 "하위 카드에 업무를 위임할 때 다음 AI 설정을 사용하세요"를 넣었다.
- 이 문구는 서버 규칙과 겹친다. 그래서 2026-11-09 사용자 결정으로 코드와 브라우저 저장값은 남기고 미사용으로 고정했다(`AI_DELEGATION_DIALOG_SETTING_AVAILABLE = false`, `src/utils/aiDelegationRuntimeSelection.mjs`).
- 화면에는 체크를 끈 비활성 상태와 「계정 메뉴의 AI 위임 규칙 적용」 안내만 보인다. 저장된 사용 설정이 있어도 문구를 전달하지 않고 저장값도 바꾸지 않는다.
- 다시 쓰려면 이 상수를 true로 바꾼다. 다만 서버 규칙과 함께 쓰면 AI가 그 문구대로 적은 설정이 규칙 값으로 바뀌므로, 예외(`aiPolicyOverride`) 연결을 함께 검토해야 한다.

## 이미 퍼진 규칙 사본

총괄·문서 루트 AI 대화에는 2026-11-09 규칙 표가 주입돼 있고, 문서 루트 카드 설명과 일부 하위 카드에 사본·주석이 있다.

- 지금의 표와 같으므로 당장 충돌은 없다.
- 다음에 규칙이 바뀌어도 대화에 알리지 않는다. 옛 값으로 위임하면 서버가 바로잡고 응답으로 알린다.
- 카드 본문에 남은 앞으로의 위임 설정 문구는 「위임 AI 설정은 MnP 위임 규칙을 따른다」로 바꾼다. 과거 실행 기록은 그대로 둔다. 이 정리는 AI 대화를 깨우지 않고, 별도 승인을 받아 한 번에 처리한다.

## 루트 카드 CLI 전환 인계

2026-11-11 결정: 문서 루트 담당의 CLI가 규칙과 달라지면 일치하는 보조 대화를 곧바로 담당으로 삼지 않고 기존 담당의 인계 절차를 거친다. 2026-11-14부터 같은 CLI 안의 모델 변경은 현재 담당 대화에서 수행하며, 하위 카드에서 CLI가 달라지는 경우만 기존 최신 일치 후보 규칙을 유지한다. 설정 저장만으로 모든 AI를 깨우지는 않으며 다음 그룹 문서 지시를 받을 때 처리한다.

1. 지시 전문을 `queued`로 저장하고 `rootHandoff`에 요청 ID·이전 담당·설정·문서 내용 해시를 고정한다. 기존 위임·복구·완료 보고가 남아 있거나 기존 담당이 응답 중이면 기다린다.
2. 기존 담당에게 인계문 작성만 요청한다. 승인 범위, 사용자 결정·대기 지시, 결과와 증거, 미완료 사항, 지시 ID와 회신 대상을 포함한다. 기존 담당은 서버가 지정한 `requestId`와 설정으로 `mindnprogress_start_card_conversation`을 호출한다.
3. 후속 대화는 같은 머신에서 인계문·최신 카드·그룹 기준만 확인하고, 같은 도구에 `resultOnly=true, acceptHandoff=true`를 보내 인수를 확인한다. 이 확인은 후속 대화만 할 수 있으며 업무 실행 승인을 추가하지 않는다.
4. 실제 모델·사고 강도·모드가 요청과 일치하고 후속 대화의 인수를 확인해야 담당을 전환한다. 인수 턴 종료 후 보관한 업무를 새 담당에게 한 번 전달한다. 기존 대화는 보존한다.

인계 중 문서 내용·그룹 기준·담당이 바뀌면 자동 업무 전달을 중단한다. `GROUP_DOCUMENT_INSTRUCTION_HANDOFF_*` 사유와 `rootHandoff`로 진행을 확인한다. 원격 응답 유실·재시작 시 저장한 operation/request ID로 조회하여 중복 생성·전송을 막는다. 인계 실패·기존 AI 미응답을 빈 새 대화 생성으로 대체하지 않는다.

내용 해시 버전 2(`rootHandoff.documentHashVersion=2`)는 객체 속성 순서를 정렬해 비교한다. 저장 정규화로 속성 순서만 바뀌어도 내용 변경으로 오인했던 첫 필드 시험 오류를 수정했으며, 배열 순서와 실제 값의 변경은 계속 감지한다.

구버전 기록은 서버 시작 시 접수 당시 해시와 일치하는 현재 원문 또는 가까운 이력(접수 이후 최신 64개 이내)을 먼저 확인한 뒤, 현재 문서와 내용이 같을 때만 버전 2로 변환한다. 이전 해시와 증거 이력 ID는 `legacyDocumentHash`·`hashUpgrade`에 남긴다. 이 오류로 실패한 지시는 후속 대화의 인수 기록이 있고 총괄 문서 버전·그룹 기준·기존 담당이 유지되며 이후 새 지시도 없을 때만 대기 상태로 복구한다. 기존 대화·요청 ID·첫 메시지·인수 확인은 보존하고 실제 실행 설정 검증부터 이어간다. 증거가 없거나 내용이 바뀌었다면 기대 해시를 현재 값으로 덮어쓰지 않고 기존 차단 상태를 유지한다.

기존 위임의 보고 주소·소유권과 외부 회신 주소는 바꾸지 않는다. 기존 보고를 모두 수신한 뒤 인계하며, 새 그룹 지시는 새 담당을 사용한다. 현재 서버 인계는 동일 머신만 지원한다.

수동 `start_card_conversation`도 실제 실행 설정이 요청값과 일치한 후 대표 연결을 전환한다. 자동 루트 인계에만 후속 대화의 명시적 인수 확인을 추가로 요구한다.
