## 롤백을 택한 이유

- **확인**: 사용자가 롤백을 택하면서 이유를 직접 설명한 문장은 대화 기록에서 찾지 못했다. 롤백 직전의 공통 맥락은 세 가지다. "고도화 이후 AI 작업이 잘못되는 경우가 발견됐다"는 관찰, 원인 확정이 불가능하다는 판단(2×2 비교 0/4회), 그리고 진행 중인 검증이 실제 실패 유형을 판정하지 못한다는 확인이다.
- **확인**: 롤백 범위를 정할 때 AI 쪽 판단 근거가 대화에 남아 있다(`d0aa6ead` 15:31). workflow/writePolicy, 역할별 노출, new/resume/recovery 빌더 같은 지침 구조 변경은 AI가 받는 문맥을 계속 바꾼다. 그래서 일부라도 남기면 롤백 효과를 확인할 때 원인 판단이 흐려진다는 것이다. 그 결과 지침 구조는 모두 되돌리고 독립적인 안전 안내·제품 검증 로직·테스트 개선만 분리 보존했다([preserved-improvements.md](preserved-improvements.md)).
- **추정**: 원인을 확정할 수 없는 상황에서, 고도화 전 기준선에서는 같은 유형의 이상이 보고되지 않았다는 점이 기준선 복귀를 택하게 한 실질적 이유로 보인다.

## 확인된 결함(경량화 구현 자체의 문제)

아래는 09-30 재감사와 10-01 비교에서 Git으로 확인된 결함이다. 일부는 `60f4e51`에서 보완된 뒤 롤백됐다. 이 결함들이 관찰된 행동 이상의 원인이었는지는 확인되지 않았다.

- 카드를 선택하지 않은 진입 응답에 `binding.state=bound`가 표시됐다.
- 직접 시작한 일반 카드도 `worker`로 표시됐고, 분석 요청에도 `writePolicy=allowed`가 표시됐다.
- 작업공간 대기열에서 재개한 위임에 `resume` 상태 전달이 빠지는 경로가 있었다.
- 11개 도구의 고유 조건이 도구 설명에서 빠졌다.
- 지식선 판단 기준과 외부 대기·재개 절차가 공통 지침에서 온전히 남아 있지 않았다.
- 경량화 커밋이 기존의 세부 의미 검사를 짧은 문구 검사로 바꿨다. snapshot·도구 표면 테스트는 "현재 문구와 fixture가 같다"만 확인했고, 고도화 전 행동 계약이 보존됐는지는 검사하지 않았다.

## 원인 가설

모두 **추정**이다. 서로 배타적이지 않다.

1. **상세 규칙의 축약·분산**: 처음 받는 제품 규칙이 짧아지고 나머지가 역할별 조회와 도구 설명으로 흩어졌다. AI가 필요한 조회를 건너뛰거나 짧은 안내만으로 판단하면 완료 조건과 검증 근거를 덜 챙길 수 있다. `관전중` 사례에서 직접 확인된 실패는 위임 범위·완료 기준 설정과 검수였다. 이것이 이 가설과 맞는 유형이지만 인과는 검증되지 않았다.
2. **경량화 초기 구현 결함**: 위 "확인된 결함"의 역할 오분류와 바인딩 표시 오류가 잘못된 권한·역할 판단을 유도했을 수 있다.
3. **모델 영향**: 고도화와 문제 구현에 쓰인 GPT-5.6-Sol의 품질 저하 제보가 같은 시기에 있었다. 이후 GPT-5.6-Sol 등의 새 위임·대화 재사용을 제한하는 별도 모델 정책이 들어갔다(`4d57e9a`, `c541fd7`). 모델 정책은 지침 효과의 증거가 아니다.
4. **검증 공백**: 개정의 합격 기준이 문구·문자 수·unit 통과였다. 행동이 나빠져도 개정 단계에서 드러날 수 없었다. 이 공백 자체는 **확인**된 사실이다.
5. **목표 희미화**: 긴 위임·검수 체인에서 AI가 원래 목표를 수단(간결화)으로 바꿔 말한 사례가 있다(09-22, 10-01). 10-02에는 사용자가 별도 작업에서 "AI는 목표가 무엇이었는지 점점 희미해지는 현상"을 지적했다(대화 `a46bf65b`). 지침 분량과의 관계는 확인되지 않았다(관찰).

## 다음 개정에서 피할 방식

롤백 교훈으로 정리한다. 서버 guide·도구 설명·전달 전문과 MnP 작업에 쓰이는 스킬에 적용한다.

- 상세 규칙을 포인터("guide.X를 따르세요")나 다른 조회 결과로 옮겨 처음 받는 문맥에서 빼는 축약은 하지 않는다. 옮겨야 한다면 행동 평가로 같은 행동이 유지됨을 먼저 보인다.
- 역할·상태별 조건부 노출로 규칙을 빼는 변경은 역할 판정이 정확하다는 검증과 행동 평가를 거친 뒤에만 한다.
- 문자 수 절감을 성공 기준으로 쓰지 않는다. 크기는 경고선으로만 관리한다(`tests/fixtures/ai-instruction-budget.json`의 `responseSizes`).
- 중복 제거는 같은 응답 안에 같은 문장이 그대로 반복되는 경우에만 한다. 표현이 다른 유사 문장은 각각의 맥락이 있으므로 남긴다.
- 지침 구조 변경과 독립적인 안전·제품 개선을 한 커밋에 섞지 않는다. 이번 롤백에서는 혼합 커밋 4개를 파일 안의 변경 단위로 나눠 판정해야 했다([target-inventory.md](target-inventory.md)).
- 개정 전후로 [behavior-evaluation-checklist.md](behavior-evaluation-checklist.md)의 대표 시나리오를 같은 모델로 실행해 행동 결과를 비교한다.
- 스킬이 "서버가 알려준다"며 서버 규칙에 의존하는 절은, 서버 guide를 축약할 때 함께 재검토한다.

## 롤백 기준선 재생성 기록

`baseline-guide-sources.json`과 `initial-response-evidence.json`은 처음에는 11a5079 Git 기준선 재현이었지만, 아래 승인에 따라 작업 트리 기준으로 다시 만들었다. 이 폴더의 다른 문서가 말하는 "기준선 원문"은 11a5079 원문이며, 지금 파일과 다르다.

- 재생성 절차: `node scripts/capture-guidance-evidence.mjs --rebaseline-working-tree --approval-ref "<사용자 승인 위치와 내용>" --approved-at YYYY-MM-DD`. 사용자가 승인한 경우에만 실행한다. `tests/initial-guidance-restoration.test.mjs` 등 지침 테스트의 실패를 해소하려고 재생성하지 않는다. 스크립트는 승인 근거가 없거나 이미 사용한 승인 근거이면 거부하고, 기준선 파일에 커밋되지 않은 변경이 있어도 거부한다. 이미 승인된 재생성 기록(`rebaseline`)이 있으면 새 승인 근거를 주어도 기본으로 거부한다. 사용자가 기준선 교체를 승인한 경우에만 `--replace-rebaseline-head <기록된 rebaseline.head 전체 SHA>`를 함께 지정하며, 기록된 head와 정확히 일치하지 않으면 거부한다. 이 교체 인자 검사는 2차 재생성을 실행한 뒤 같은 R1 검수 보완에서 추가했다. 재생성하면 테스트의 `APPROVED_REBASELINE` 상수도 함께 바꿔야 하므로 기준선 교체가 diff에 드러난다.
- 응답 크기 상한은 경고선으로만 쓴다. 상한을 넘으면 테스트는 진단 경고만 남긴다. 금지·예외 문장을 삭제·축약해 상한에 맞추지 않는다.
- 1차 재생성(2026-10-22, 커밋 `ae54629`): 승인 근거는 사용자 결정 "MnP 롤백 기준선을 현재 상태로 다시 만든다(기존 실패 3건 해소)"이다. 이때 스크립트는 승인 기록을 고정 문자열로 남겼고, 같은 명령을 다시 실행해도 거부하지 않았다. 2차 재생성 때 이 두 가지를 고쳤다.
  - 캡처 출처는 `7b04f8f` 위의 미커밋 작업 트리다. 2026-10-22 복구 작업에서 대조한 결과, 기록된 소스 9개 원문은 `ae54629` 커밋의 같은 파일과 EOL 외에 같다. untracked 3개 해시도 `ae54629` 파일과 일치한다(`mcp/documentViews.mjs`·`mcp/workspacePoolStatusGuide.mjs`는 LF, `server/lib/aiDelegationResultCapture.mjs`는 CRLF 기준). 따라서 1차 재생성 기준선은 `ae54629` 커밋 트리에 대응한다.
