# AI 한도 중단 복구 검토

사용량 한도는 정상적으로 발생할 수 있는 실행 중단이다. 업무 완료 여부, AI 실행 여부, 작업공간 소유권, 상위 결과 전달 여부를 각각 보존하고 제품이 복구를 관리해야 한다. 복구를 수행할 AI가 먼저 자신의 실행 상태를 고쳐야 하는 구조는 피한다.

## 확인한 원인과 변경

| 경계 | 기존 문제 | 보완 |
| --- | --- | --- |
| 작업공간 보존 | 변경 없는 실패는 lease를 취소하고 세션을 제거하여 한도 대기 위임만 남음 | 한도 중단은 변경 유무와 무관하게 소유권과 세션 보존 |
| 작업공간 재개 | 변경이 있는 작업은 격리한 뒤 dirty 상태라서 복구도 거부함 | 동일 소유권·브랜치·HEAD를 확인하고 커밋 전 변경을 보존한 재개 허용 |
| 풀 재시작·다른 작업 배정 | 변경 없는 격리 lease가 자동 회수 후보에 포함됨 | 한도 중단 lease를 회수 후보에서 제외 |
| 구버전 기록 | 이미 반납한 failed-clean lease는 복구 가능 상태로 인식하지 못함 | 서버 기록의 문서·카드·대화·한도 원인을 검증하고 복구용 lease 배정 |
| 복구 권한 | 원래 상위 AI 대화만 재개할 수 있어 그 AI의 한도가 소진되면 도움을 받기 어려움 | 같은 상위 카드에 연결된 현재 AI 대화도 요청 가능, 다른 카드·연결 없는 대화는 거부 |
| 사용자 접근 | 그룹 총괄 화면 중심으로만 복구 동작 제공 | 개별 카드 세부 정보에서 상태 확인·기존 작업 재개·결과 재전달 제공 |
| 요청 재전송 | pendingRecovery가 있어도 앞선 상태 검사에서 거부되어 기존 요청 확인 분기에 진입하지 못함 | 기존 요청 확인을 허용하고 새 실행 없이 전달 불확실 상태 안내 |
| 운영 알림 | 한도 대기가 상위 실행 복구 알림 경로에서 빠짐 | 사용자에게 중단과 카드 복구 위치를 중복 없이 알림 |

## 상태별 처리

- `waiting-usage-limit`, `waiting-rate-limit`: 미완료 작업이다. 자동 조회는 가능하지만 한도가 해제되었다고 추측해 AI를 자동 실행하지 않는다. 사용자 재개 요청 또는 기존 승인 범위의 AI 복구 요청으로 이어간다.
- `parent-wake-failed`와 작업 성공: 하위 작업을 재실행하지 않고 저장된 결과 전달만 재시도한다. 원문이 없으면 다른 턴의 최신 응답을 대체 결과로 사용하지 않는다.
- `pendingRecovery`: 복구 요청을 보냈지만 접수 확인이 끝나지 않은 상태다. 같은 operation을 조회하여 복원한다. 404나 연결 장애만으로 새로운 작업을 만들거나 이전 요청을 완료 처리하지 않는다.
- 격리 작업공간의 소유권·HEAD 불일치, 진행 중인 Git 작업, 충돌: 일반 한도 재개로 우회하지 않고 검증 오류를 반환한다.
- 이미 반납된 과거 lease: 같은 위임·대화를 유지하고 MindNProgress만 복구용 작업공간을 배정한다. 배정 기록을 보존해 응답 유실 뒤 중복 배정을 막는다.

## 검증

- 실제 임시 Git 저장소에서 변경 없는 중단, 추적 파일 수정과 새 파일이 있는 중단을 각각 재현한다.
- 중단 후 서버의 풀 관리자를 재시작하고 다른 작업 배정을 시도해 기존 세션·브랜치·변경이 보존되는지 확인한다.
- 같은 lease를 재개한 뒤 다시 한도에 막혀도 두 번째 복구와 이력 보존이 가능한지 확인한다.
- 구버전에서 반납한 작업은 새 lease를 한 번만 배정하며, 재시작 후에도 그 lease를 사용하고 다른 카드 요청은 거부한다.
- 서버 API에서 같은 카드의 새 상위 AI, 사용자와 AI의 동시 복구, 보고 실패, 전달 응답 유실과 실행 기록 404를 검증한다.
- 격리된 브라우저에서 하위 카드 표시, 다른 카드 제외, 확인 취소, 복구 API 대상 문서·버전, 서버 오류, 보고만 재시도하는 동작을 검증한다.

## 적용과 남는 경계

서버 코드 반영에는 MindNProgress 재시작이 필요하다. 진행 중인 작업의 중단을 피할 수 있는 시점에 적용한다. 이 변경은 AI 제공자의 한도를 해제하거나 다른 모델로 전환하지 않는다.

AionCore가 기존 operation을 잃고 복구 요청의 실제 실행 여부도 확인할 수 없는 경우는 사용량 중단 자체와 구분한다. 이때 안전한 자동 재실행에는 AionCore 측의 영속 실행 기록과 취소·종료 확인 계약이 필요하다. 현재 변경은 그 상태를 숨기거나 성공으로 처리하지 않으며, 실행 상태가 불명확한 요청의 중복 실행을 막는다.
