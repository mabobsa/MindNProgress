# MnP 저장 공통 계약 v1

REQ-MNP-01이 02~07에 제공하는 구현 계약이다. [현재 코드 감사](audit-20261027.md)의 결함과 구분한다. 여기의 새 보장은 해당 소유 카드가 구현·검증한 뒤 성립한다. 코드·운영 정책은 이 문서 작성으로 변경되지 않는다. 파일 저장 방식을 유지하며 저장 무결성, 충돌, 중복 요청, 취소와 조회의 접점을 확정한다.

## 1. 자원과 잠금 순서

지원 조건은 데이터 루트 하나에 콘텐츠 작성 API 프로세스 하나다. 동일 루트의 복수 API나 서버 실행 중 직접 JSON 편집은 지원하지 않는다. MCP의 프로세스별 사용량 shard는 별도 자원이다. 운영 복원·직접 자산 정리는 서버가 정지한 기존 절차에서만 한다. 이 계약은 프로세스 간 분산 잠금을 도입하라는 요구가 아니다.

모든 콘텐츠 변경은 최초 권위 있는 읽기부터 조건 검사·후보 생성·저장 확정·캐시 무효화까지 같은 보호 문맥에서 실행한다. `saveMap` 마지막 rename만 잠그거나, 잠금 밖에서 만든 전체 배열을 잠금 안에 넣어 저장하지 않는다. `withResources(keys, operation)` 같은 공통 진입점을 02가 소유하며, 하위 저장 도우미에는 획득된 문맥을 전달한다. 같은 키를 재획득하는 중첩 호출은 금지한다.

| 순위 | 키 | 보호 대상 |
|---|---|---|
| 0 | `catalog` | 문서의 생성·영구 삭제·소속/배치 및 Ref 대상 집합이 변하는 작업. 구조 변경 집합의 탐색·재검증을 보호하는 RW gate. |
| 1 | `doc:{mapId}`를 mapId의 코드포인트 오름차순 | 해당 map JSON, 댓글 배열, 그 문서의 lifecycle 판단, revision·일일 backup·이미지 참조. 문서와 댓글을 별도 최상위 잠금으로 나누지 않는다. |
| 2 | `state:{상대 파일 경로}`를 오름차순 | `_map-order.json`, `_document-lifecycle.json`, `_group-projects/{g}.json`, 귀속/origin/위임/지시/이동 이력 등 공동 변경 파일. 상대 경로를 정규화하고 루트 탈출을 거부한다. |
| 3 | `notification:{userId}`를 오름차순 | 사용자별 알림 전체 RMW, 읽음 처리, 생성·삭제·귀속 보정. |

ID 비교는 locale 정렬을 쓰지 않는다. 획득은 오름차순, 해제는 역순이다. 획득 중 실패·취소되면 이미 잡은 키도 모두 해제한다. 대기 도중 잠금 승격, doc 보유 후 catalog 획득, notification 보유 후 doc 획득은 하지 않는다. 기존 group/reconstruction/request Q가 이 순서를 역전하지 않도록 어댑터로 통합한다. 같은 파일의 기존 persist Q와 새 자원 잠금을 병렬 소유자로 두지 않는다.

`catalog` 공유는 Ref/계층/순서 변경처럼 전역 참조 탐색에 영향을 주는 구조 변경에 사용한다. 생성·삭제·이동·보관/휴지통·재구성처럼 집합과 수명주기를 전환하는 작업은 독점을 사용한다. 단일 문서의 일반 필드·댓글·알림 변경은 catalog를 잡지 않고 자신의 키만 사용한다. 따라서 전환과 무관한 문서의 본문/댓글 변경은 병렬로 계속할 수 있다. 구조상 참조 대상을 바꾸지 않는 지식선 변경도 해당 문서 키로 처리할 수 있으나, Ref의 원본/대상 변경은 catalog 대상이다.

다중 작업은 잠금 밖에서 외부 상태와 후보 자원을 수집하고, catalog가 필요한 경우 먼저 획득한 뒤 자원 집합을 다시 확정한다. 영향받는 원본·대상·Ref 문서와 댓글, 관련 상태·알림 키 전체를 정렬 획득한 후 문서·댓글·lifecycle·권한·AI 실행 예약을 다시 읽는다. 키 집합이 늘어나면 모두 해제하고 같은 요청·기한 안에서 다시 수집한다. 최대 3회 뒤 `RESOURCE_SET_CHANGED` 충돌로 종료한다. 늦게 발견한 키를 역순으로 추가하지 않는다.

잠금 키는 카드가 아니라 저장 자원이다. 서로 다른 문서여도 동일 사용자 알림을 쓰면 짧은 알림 커밋은 직렬화된다. 공용 state 파일도 실제 교체 구간만 직렬화하며, 모든 문서를 하나의 큐로 묶지 않는다. 외부 Runner/AionUi/Git/모델 응답을 자원 잠금 안에서 기다리지 않는다. 외부 작업은 예약→잠금 해제→외부 수행→동일 예약 토큰/자원 버전 재검증→로컬 확정으로 분리한다. 외부 수행이 있던 예약은 시간 초과만으로 훔치지 않는다.

## 2. 공동 변경과 수명주기

| 연산 | 확정 범위와 사전 조건 |
|---|---|
| 일반 카드·본문·댓글 | `doc:m` 아래 현재 문서·카드 존재와 활성 상태를 확인한다. 댓글 추가/답글은 현재 카드·부모 댓글을 확인하고 새 배열을 만든다. 반응 toggle도 같은 논리 요청의 재전송으로 두 번 실행하지 않는다. |
| 카드 삭제 | 현재 제품 의미대로 map의 카드·관계만 변경하고 기존 댓글·이력·이미지를 임의로 물리 삭제하지 않는다. 이후 해당 카드의 새 댓글은 거부한다. 남아 있는 댓글의 열람 정책은 기존 동작을 유지한다. |
| 문서 간 이동 | source/target, 들어오는 Ref 문서, 양쪽 댓글, 이미지 복사, 귀속/origin, 관련 완료 위임·그룹 지시, 기존 알림 경로·이동 이력을 하나의 공동 변경으로 확정한다. 처리 중 위임/실행 대기는 기존 기준으로 거부한다. 원본/대상 버전·댓글 해시·수명주기·참조 집합을 검증한다. |
| 보관·휴지통·복원 | content version과 별개로 `lifecycleVersion`을 증가시킨다. 현재 보관 metadata와 map의 trash 상태를 하나의 상태로 판단한다. 활성 여부의 읽기와 저장 사이 전환을 허용하지 않는다. 오래된 활성 스냅샷을 복원 후 다시 적용하려면 lifecycle 조건을 재검토한다. |
| 이력·일일 백업 복원 | 현재 문서 버전+lifecycleVersion과 선택한 스냅샷 해시를 조건으로 전체 내용을 교체한다. 기존 현재본의 revision/사전 backup을 보존한다. 댓글은 현재처럼 복원하지 않는다. 더 최신 댓글을 과거 시점으로 되돌리지 않는다. |
| 재구성·되돌리기 | 기존 승인·원본/댓글 해시·그룹 기준·Ref 영향·실제 렌더 검증을 보존한다. preparing 중 재시작은 기존처럼 원본 유지·미완성 후속 보관으로 수습한다. applied 이후에는 일반 트랜잭션 복구와 전환 기록이 모순되지 않아야 한다. |
| 영구 삭제 | 모든 대상이 휴지통이고 활성 AI/작업공간 처리가 없음을 재검증한다. 삭제 manifest와 상태 기록을 확정하고 동일 삭제를 재개할 수 있어야 한다. 일부 파일 삭제 뒤 실패한 상태를 정상 활성 문서로 내보내지 않는다. 이미 삭제된 문서를 복원할 수 있다는 성공을 반환하지 않는다. |
| 예약·일일 백업·귀속 복구 | 요청 경로와 동일 자원 경계를 사용한다. 새 버전의 일일 백업을 오래된 snapshot으로 덮지 않는다. 댓글/알림 귀속 보정의 의미는 보존하되 최신 배열에 적용한다. |

일반 `saveMap`의 내용 무변경은 버전 증가·revision·새 알림을 만들지 않는다. 댓글만 바뀌면 문서 content version은 증가시키지 않고 댓글 집합 revision 또는 정확한 해시를 갱신한다. 읽기 응답에는 문서 버전·lifecycleVersion·댓글 revision/해시를 구분하여 제공한다.

## 3. 충돌과 변경 전 조건

조건은 잠금 안에서 검증한다. 모든 field 값 비교는 속성 없음과 `null`을 구분하고 텍스트 SHA-256은 실제 UTF-8 원문으로 계산한다. 객체 digest는 키 정렬·배열 순서 유지 규칙을 공유한다. 권한·AI 귀속·Ref 원본 소유·체크리스트 집계·대기 해제 규칙을 조건 완화로 우회하지 않는다.

| 변경 종류 | 필요한 읽기 집합·충돌 범위 |
|---|---|
| 카드 필드 | mapId/cardId/field별 이전 값 또는 해시+카드 존재/종류/Ref 원본 조건. 서로 다른 필드·카드 변경은 최신 map에 적용한다. 같은 조건을 읽고 만든 변경만 충돌 범위다. |
| 본문 부분 수정 | 기존 `expectedSha256` 및 `replace_once`/`replace_between` 경계 유일성. 서버 보호 구간에도 검사를 전달한다. 기존 MCP의 동일 해시 재검사는 재사용한다. |
| 공유 지식 검토 | 본문 SHA뿐 아니라 검토에 실제 사용한 description·카드 종류/Ref·관계·댓글·원본 출처의 해시/버전 집합을 검토 context token으로 전달한다. 03이 기존 검토 문맥의 read-set을 직렬화한다. 관련 없는 카드만 변했으면 적용, 의존성이 바뀌면 재검토. |
| 댓글 편집·해결·반응·삭제 | 본문 편집은 summary+detail+legacy text를 포함한 content hash. 해결은 이전 해결 상태, 반응은 해당 actor/emoji membership, 삭제는 대상과 답글 집합의 조건. 다른 댓글의 추가 자체는 본문 편집 충돌이 아니다. |
| 관계·계층·순서·삭제 | 변경 edge/node의 이전 값, 원본/대상 존재, 이동 부모·형제 순서·삭제 자식/Ref 등 실제 읽기 조건. 안전한 독립성 입증이 없는 구조 변경은 전체 문서 버전 조건을 유지한다. |
| 전체 PUT·복원·명시적 전체 교체 | 최신 baseVersion과 lifecycleVersion 필수. `force`를 자동 충돌 우회로 사용하지 않는다. 레거시 force의 명시적 사용자 덮어쓰기 기능은 별도 명시 정책으로 유지하되 자동 클라이언트는 사용하지 않는다. 조건 없는 기존 요청을 조용히 세밀한 병합 요청으로 해석하지 않는다. |

03은 세밀한 사전조건 입력을 선택적으로 확장한다. 새 read-set이 없는 기존 content-patch 요청은 전체 baseVersion을 엄격 적용한다. 새 계약 요청은 baseVersion을 순서 정보로도 돌려주되 독립 read-set이 모두 같으면 전역 문서 버전 차이만으로 거부하지 않는다. 02 단계에서는 기존의 엄격한 409를 허용한다. 03 완료 후 독립 카드/필드 20개는 모두 보존되어야 한다.

충돌 응답은 HTTP 409와 기존 code를 보존하면서 `reasonCode`, `conflicts:[{resource,cardId,field,expected,current,kind}]`, `outcome:'not-applied'`, `retryable:false`를 제공한다. 큰 본문은 노출하지 않고 해시·버전으로 설명하며 현재 권한 안의 값만 반환한다. 필드 충돌은 `FIELD_CONFLICT`, 읽기 의존성은 `READ_DEPENDENCY_CHANGED`, 수명주기는 `LIFECYCLE_CONFLICT`로 구분한다. 기존 `VERSION_CONFLICT`, `TEXT_HASH_MISMATCH`, 검토 오류와 호환 매핑을 남긴다.

충돌을 받았다는 이유로 새 원문에 대한 기대값을 자동으로 바꾸지 않는다. 실제 사용자가 새 상태를 검토해 의도를 바꾸면 새 논리 요청이다. 현재 웹의 “겹치면 내 변경 유지” 전환은 기존 별도 부분 수정 업무가 소유하며, 이 동작을 03 서버의 충돌 보장이 이미 해결했다고 보고하지 않는다.

## 4. 확정 저장과 재시작 복구

성공은 권위 데이터와 결과가 확정되고 해당 자원이 읽기에 노출 가능한 상태라는 뜻이다. 단일 JSON rename 성공, 2xx 수신, 부수효과 시도 완료만으로 다중 자원 성공을 판정하지 않는다.

02는 잠금 안에서 공동 변경의 모든 후보·조건을 먼저 준비하고 실패 시 같은 보호 범위에서 일관성을 회복하는 경계를 만든다. 04는 그 경계에 **트랜잭션별 영속 journal과 redo 복구**를 구현한다. 별개의 데이터 파일과 결과 파일을 각각 저장하고 두 저장의 동시 성공을 가정하지 않는다. 02 완료만으로 04의 재시작·중복 요청 보장을 주장하지 않는다.

일반 저장 journal의 규격은 다음과 같다.

1. `_storage-transactions/{transactionId}/intent.json`에 schemaVersion, 논리 요청 ID·scope·digest, 잠금 키, 각 파일의 before/after 해시와 after-image 또는 삭제 표식, 결과 요약, 알림/백업/SSE side effect ID를 기록한다. 바이너리/대형 after-image는 같은 디렉터리의 파일과 해시로 참조한다. 경로는 데이터 루트 내부의 명시된 자원만 허용한다.
2. intent와 after-image를 완전히 쓰고 닫은 뒤 `commit.json`을 임시 파일→교체로 기록한다. 이 marker가 논리적 확정점이다. marker 이전에는 권위 파일을 교체하지 않는다. 준비 파일 실패는 정리하고 `not-applied`로 끝낼 수 있다.
3. marker 이후에는 취소나 일반 rollback을 하지 않는다. 기록된 after-image를 각 파일에 반영하고 메모리 상태·캐시를 동기화한다. 데이터·필수 revision·공동 변경 상태가 모두 반영된 뒤 `applied.json`을 기록하고 잠금을 해제한다. 결과의 원본은 journal이므로 별도 결과 인덱스는 파생 데이터다.
4. `applied` 기록 전에는 겹치는 자원의 다음 트랜잭션과 해당 자원의 읽기를 통과시키지 않는다. 무관한 문서 읽기는 계속 가능하다. 중간 I/O 실패는 해당 자원을 복구 대기로 유지하고 `not-applied`로 거짓 응답하지 않는다.
5. 시작 시 요청 수신·migration·background scheduler보다 먼저 복구한다. marker 없음은 준비 파일 정리, marker 있고 applied 없음은 redo, applied 있음은 재반영하지 않는다. redo 시 각 대상이 before 또는 after 해시인 경우만 진행하며 둘 다 아니면 `RECOVERY_REQUIRED`로 해당 자원을 격리한다. 조용한 덮어쓰기는 금지한다. applied 기록 후에만 후속 동일 자원 작업을 허용하므로 앞선 미완료 journal이 뒤 트랜잭션을 덮는 경우를 방지한다.
6. 새 프로세스의 결과 조회는 journal에서 같은 요청의 확정 결과를 복원한다. 영구 삭제와 다중 문서 이동도 같은 규약을 사용한다. 재구성의 기존 preparing 복구는 전환 orchestration으로 유지하며, 개별 생성/최종 lifecycle 커밋의 journal 복구가 먼저 끝난 뒤 그 상태를 판단한다.

기존 rename 재시도 도우미를 재사용할 수 있다. intent·after-image 준비의 write/close/sync 실패는 marker 이전 실패로 처리한다. marker 교체 결과가 불명확하면 유효한 marker를 재조회하여 확정 여부를 판정하고 `not-applied`로 단정하지 않는다. applied marker를 완전히 기록한 뒤에만 다음 겹치는 작업을 허용한다. marker 이후 I/O 실패는 복구 대상으로 유지한다. 일반 로컬 파일시스템에서 **서버 프로세스만 종료되고 OS·디스크는 유지되는 재시작**을 검증 범위로 삼는다. Windows 정전·OS crash·디스크 write-cache 유실·볼륨 손상까지의 내구성은 보장하지 않는다. 단일 파일의 `fsync`만으로 다중 파일 정전 원자성을 선언하지 않는다.

revision은 트랜잭션의 필수 일부이며 동일 transaction/effect ID로 중복 생성하지 않는다. 일일 backup과 새 알림은 확정 journal에 후속 처리 항목으로 남기고 실패하면 `sideEffectsPending`에 드러낸다. 기존의 데이터 저장 성공 뒤 backup 경고 허용을 유지하면서, 실패 항목의 재개 근거를 잃지 않는다. 이미 있는 알림의 mapId 변경·삭제처럼 공동 변경의 참조 일관성에 필요한 변경은 본 트랜잭션에 포함한다.

후속 처리 항목은 `transactionId/effectKind/recipient-or-resource`의 안정 ID로 멱등 적용한다. 알림 파일 변경과 처리된 effect 기록도 하나의 journal 커밋으로 묶으며, 단순히 알림 배열에서 같은 ID를 찾는 것만으로 끝내지 않는다. 알림 최대 200개 표시에서 오래된 알림이 빠져도 처리된 effect의 영속 기록을 근거로 중복 생성하지 않는다. 일일 backup은 최신 버전·날짜를 확인해 오래된 후속 처리가 새 backup을 덮지 않게 한다. SSE는 네트워크 exactly-once를 약속하지 않고, 확정 후 안정 event ID로 발행하며 재연결 시 최신 snapshot을 읽는다. 이 계약을 Dooray/AionUi/Runner 외부 실행의 전역 단일 실행 보장으로 확대하지 않는다.

## 5. 요청 식별과 결과

04는 기존 HTTP/MCP 변경 입력에 선택적 `requestId`와 결과 조회 모드를 추가한다. 새 MCP 도구는 만들지 않는다. HTTP는 `Idempotency-Key` 헤더, MCP는 기존 도구의 `requestId`를 사용한다. `resultOnly:true`는 같은 기존 도구에서 `X-MNP-Result-Only: 1`로 전달하며 해당 요청의 결과만 조회하고 저장을 시작하지 않는다. 조회는 ID와 현재 scope로 처리하고 본문 재전송을 요구하지 않도록 기존 입력의 조회 모드를 구분한다.

ID 형식은 `mnpw:{13자리 생성시각 밀리초}:{32자리 난수 hex}`다. 한 논리 요청의 모든 재시도에서 ID·의도·읽기 조건을 그대로 보존한다. 클라이언트는 요청을 최초 전송하기 전에 ID를 생성·보존한다. 새 요청 허용 시각은 서버 기준 과거 24시간~미래 5분이다. 이 범위를 벗어난 미등록 ID는 `410 REQUEST_EXPIRED` 또는 미래 시각 `400 REQUEST_TIME_INVALID`로 거부한다. 시간이 지나 기록이 정리된 옛 ID가 새 변경으로 재실행되지 않도록 한다.

완료/거부 결과는 **terminal 시점부터 최소 24시간** 보존한다. 처리 중·복구 중 journal은 기간으로 삭제하지 않는다. terminal 결과 정리 전에도 미완료 side effect가 있으면 journal은 보존한다. 기존 보관 결과가 있으면 ID의 최초 생성 시각이 24시간을 지났더라도 동일 결과를 반환할 수 있다. 이후 처음 조회한 expired ID는 “실패했으니 새 ID로 재실행”이 아니라 보존 기간 종료로 해석하고 권위 자원에서 결과를 대조한다.

내용 digest는 정규화한 HTTP method/route/대상 IDs, 의미 있는 payload, read-set, schemaVersion, 편집자 ID·AI 대화/원래 귀속 scope를 포함한다. JSON 키 순서는 정렬하고 배열 순서·속성 없음·실제 문자열은 유지한다. 전송 기한·조회 모드·인증 token 자체는 제외한다. 갱신된 token으로 같은 주체·같은 대화의 재시도는 허용하지만 권한은 매번 확인한다.

동일 ID+동일 digest/scope는 처리 중 상태나 같은 terminal 결과를 반환하고 저장·버전·알림·revision을 반복하지 않는다. 같은 주체의 ID+다른 내용은 `409 REQUEST_ID_REUSED`다. 다른 주체/scope의 조회·재사용은 결과를 노출하지 않는 404/403으로 거부한다. 삭제 결과에는 원래 접근 scope를 보존해 문서가 사라진 뒤에도 같은 주체가 현재 활성 계정·필요 권한을 유지하면 결과를 확인할 수 있게 한다. 다른 주체나 권한이 회수된 주체에는 노출하지 않는다. 현재 권한을 되찾았다고 기록 보존 기간을 늘리지 않는다.

| 결과 | HTTP·추가 정보 | 의미 |
|---|---|---|
| 확정 성공 | 기존 200/201, `outcome:'committed'`, requestId, transactionId, 변경 자원별 version/lifecycleVersion/hash, `replayed`, sideEffectsPending | 권위 데이터가 조회 가능하다. 재전송은 같은 논리 결과·버전을 반환한다. 최신 문서 전체가 필요하면 별도 조회한다. |
| 처리/복구 중 | 202, `outcome:'processing'`, 동일 ID, retryAfterMs | 접수 또는 커밋 후 반영 중. 새 ID 실행 근거가 아니다. |
| 변경 전 확정 거부 | 4xx/503, `outcome:'not-applied'`, reasonCode, retryable | 조건 실패·권한·큐 포화 등, 변경이 없다는 판정. 일시 admission 실패는 terminal 실행 결과로 소비하지 않아 동일 ID 재시도를 허용한다. |
| 유효 ID지만 기록 없음 | 결과 조회 404 `REQUEST_UNKNOWN`, `outcome:'unknown'` | 최초 요청이 도착하지 않았을 수도 있다. 시각 유효 범위 안에서 같은 ID로만 실행/재전송 가능하다. |
| 응답 유실·클라이언트 timeout | 클라이언트 상태 `unknown` | 서버 실패 확정이 아니다. 같은 ID 결과 확인/재전송으로 수렴시킨다. |
| 복구 불가 | 503 `RECOVERY_REQUIRED`, `outcome:'processing'`, 자원 접근 차단 | 커밋을 실패로 되돌리지 않는다. 보존된 journal과 파일 조건으로 수습해야 한다. |

같은 요청의 terminal 409 조건 충돌은 동일 ID로 다시 성공하지 않는다. 검토 후 다른 내용을 보내려면 새 ID가 필요하다. 조건 거부 결과는 데이터 변경이 없는 terminal record로 영속 보존하며, commit marker가 없다는 이유로 이 거부를 미접수 요청과 혼동하지 않는다. ID 없는 레거시 소비자는 기존 응답을 유지하며 내부 transactionId는 부여할 수 있지만, 응답이 유실된 재전송의 중복 방지를 보장하지 않는다. 새 MCP 변경 경로는 04에서 ID를 사용하고, 남은 웹 소비자 전환은 기존 별도 카드가 맡는다.

## 6. 기한·취소·재시도

05의 기본값을 다음으로 확정한다. 운영 시간 측정값이나 사용자 SLA가 아니라 유한 대기 구현·시험을 위한 기술 기준이다. 설정으로 바꿀 때는 시험 manifest에도 실제 값을 남긴다.

| 항목 | 기본 계약 |
|---|---|
| 논리 요청 전체 예산 | 일반 변경 30초, 명시적 다중 문서/재구성 변경 60초. 각 재시도에서 새 예산을 주지 않는다. |
| 자원 잠금 대기 | 일반 5초, 다중 자원/수명주기 10초. 최초 대기부터 모든 키·재수집의 합계이며 전체 남은 예산보다 작아야 한다. |
| 대기열 상한 | 키당 대기 128개, 프로세스 전체 1,024개. 동일 요청 합류자는 실행 큐를 중복 점유하지 않는다. 초과는 503 `WRITE_QUEUE_FULL`, 변경 없음, retryAfterMs=250. |
| 잠금 기한 초과 | 503 `LOCK_WAIT_TIMEOUT`, 변경 없음, retryAfterMs=250. 대기자·리스너·보유한 앞선 키를 정리한다. |
| 자동 재시도 | 최초 포함 최대 3회, 기본 지연 100/200ms와 ±25% jitter. 서버 retryAfterMs가 있으면 그 값 이상 기다리고 전체 기한을 지킨다. 인증·형식·필드/의존 충돌은 자동 재시도하지 않는다. |
| rename 재시도 | 기존 6회/465ms 상한을 유지. 변경 전에는 전체 기한 확인, 커밋 후에는 안전한 복구 완료를 우선하며 timeout으로 rollback하지 않는다. |

본문 수신·크기/형식 기본 검증은 잠금 전에 끝낸다. 현재 일반 본문 2,000,000바이트 제한을 늘리지 않는다. 느린 body가 잠금을 점유하지 않도록 본문 수신도 전체 기한에 포함한다. 외부 Runner long-poll의 정상 25초와 모델·사용자 대기는 이 저장 대기 예산과 별도 단계로 기록한다.

연결 종료·취소 신호는 대기 중 또는 실제 저장 준비 시작 전이면 대기자를 제거하고 변경 없이 끝낸다. 자원 읽기·검증 후 영속 저장 준비에 들어간 작업은 연결이 끊겨도 안전한 확정/복구를 끝낸다. commit marker 뒤에는 특히 취소하지 않는다. 응답할 연결이 남아 있고 응답 예산이 끝나면 처리 중 202와 동일 ID를 제공한다. 연결이 없어도 journal 결과는 남긴다.

로그는 requestId/transactionId, 자원 ID, 대기 단계, queueWaitMs/lockHoldMs/persistMs/externalWaitMs, 재시도 수, outcome만 기록한다. 본문·token·비밀값은 기록하지 않는다. 동일 자원 안의 직렬화 대기는 허용하지만 무관한 문서가 외부 AionUi/Runner 대기 때문에 5초 예산을 넘으면 05 실패다.

## 7. 읽기와 캐시

06은 `documentReadStore.mjs`의 stat signature, generation 무효화, 진행 중 읽기 공유, 64MiB LRU, 반환 복제 규칙을 재사용한다. 파일 읽기를 마친 뒤 응답만 잘라서 개선 완료로 삼지 않는다. 카드 응답은 필요한 카드·부모/자식·선행 관계·댓글 page만 구성하며 전체 문서 clone/Ref 확장의 횟수와 bytes를 측정한다.

단일 파일 읽기는 원자 교체 전/후 중 하나만 볼 수 있다. 여러 파일을 함께 읽는 카드+댓글/Ref·문서 목록 조회는 필요한 `doc` 읽기 잠금 또는 동일 generation snapshot의 재검증으로 중간 조합을 반환하지 않는다. 이미 공유된 read promise도 커밋 generation이 바뀌면 사용하지 않는다. 전체 GET을 모든 문서 쓰기의 전역 배타 잠금으로 묶지 않는다.

무효화는 문서 내용·댓글·lifecycle·Ref 원본/원본 댓글·권한·그룹 소속별 세대를 구분한다. 다른 사용자의 권한 결과를 그대로 공유하지 않는다. 복구·복원·삭제·시작 migration도 무효화 대상이다. 성공 응답 후 재조회는 같은 확정 결과 또는 그 이후 버전을 읽어야 한다. SSE 이벤트 유실 때도 조건부 조회로 최신 상태에 수렴해야 한다.
