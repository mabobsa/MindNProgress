# REQ-MNP-02 문서·댓글 저장 무결성

출발 커밋은 `bb0fd0422b124262a6c55de0e86f863dfde4bb0b`다. [계약 v1](contract-v1.md), [작성 경로 감사](audit-20261027.md), [회귀 기준](regression-baseline.md)을 적용했다. 데이터 루트 하나에 콘텐츠 작성 API 프로세스 하나를 지원한다. 운영 서버에 배포하거나 운영 자료를 재구성한 결과는 아니다.

## 보호 경계

- `server/lib/storageResources.mjs`가 FIFO 읽기·쓰기 잠금과 비동기 보호 문맥을 소유한다. 순서는 `catalog` → `doc:{mapId}` → `state:{상대 경로}` → `notification:{userId}`이며 동일 종류에서는 코드포인트 순이다. 중첩 도우미는 보유 키를 재사용한다. 역순 추가·읽기 잠금 승격·루트 밖 경로는 거부하고 실패 시 이미 획득한 키를 해제한다.
- `server/index.mjs:requestStoragePlan/withStorageRequest`는 요청 본문을 먼저 받은 뒤 자원을 수집한다. catalog가 필요한 작업은 이를 먼저 잡고 집합을 다시 수집한다. 문서·Ref·공유 상태 키를 획득한 뒤 재검증하며 집합이 늘어나면 해제 후 최대 3회 다시 수집한다. 일반 문서 필드·댓글은 catalog를 사용하지 않는다.
- 같은 문서의 map·댓글·revision·일일 백업·이미지는 같은 doc 키다. 문서/댓글 작성, 전체·부분 변경, 공유 지식 검토, 배치, 복원은 최초 권위 읽기부터 저장 확정과 무효화까지 보호한다. 문서 조회도 해당 doc/Ref 키를 공유 모드로 사용한다. 목록·구조 조회는 필요한 catalog 공유 경계를 사용한다.
- 이동·생성·보관·휴지통·복원·영구 삭제·재구성은 catalog 독점과 관련 doc/state 키를 사용한다. 이동의 들어오는 Ref, 양쪽 댓글·이미지, 귀속·위임·지시·기존 알림·이동 이력을 함께 보호한다. 일반 휴지통·복원도 lifecycleVersion을 증가시킨다.
- 예약 백업, 일정 알림, 귀속 보정, AI 대화 연결, 위임·그룹 지시의 로컬 갱신도 같은 자원을 사용한다. 공유 메모리 저장은 잠금을 얻은 뒤 최신 값을 직렬화한다. 요청에서 시작한 백그라운드 작업은 요청의 비동기 잠금/변경 문맥을 상속하지 않는다. 만료 세션·귀속의 비동기 저장도 종료 추적에 포함한다.
- 기존 대화 삭제의 외부 보관 확인은 잠금 밖에서 수행하고 로컬 확정 시 최신 연결을 재검증한다. 폴러 전체에 문서 잠금을 걸지 않으며, 기존 AI 액션 대기는 자원 획득 전에 수행한다. 기존 액션 예약으로 대기 종료와 잠금 획득 사이 재진입을 막는다. 외부 대기·큐 한계의 전체 재설계는 05 소유다.
- 그룹 문서 지시는 queued 상태를 공개하기 전에 전달 예약을 잡는다. HTTP 작성자가 state 키를 보유한 채 같은 지시의 폴러 완료를 기다리는 역순 대기를 막는다. 기존처럼 접수 기록을 먼저 확정한 뒤 외부 전달을 수행한다. `group-project-api`는 접수 파일 준비를 멈추고 폴러를 직접 호출하여 이 경합을 검사한다.

## 공동 변경과 04 연결 위치

`server/lib/storageChanges.mjs:createStorageChanges`의 `run`이 프로세스 내 공동 변경 경계다.

1. `stage`/저장 어댑터가 파일별 before/after 후보를 모은다. 같은 문맥의 읽기는 후보를 보며 정본은 아직 바뀌지 않는다. `onRollback`으로 lifecycle·요청 기록·공유 메모리의 복구를 등록한다.
2. 모든 임시 파일 준비가 성공한 뒤 정본을 교체한다. `beforeApply`는 각 교체 직전의 어댑터 접점이다. 댓글·revision·기존 알림·삭제 파일도 후보 집합에 포함할 수 있다.
3. 실패하면 보유한 자원 안에서 역순 복구하고 메모리·캐시를 정리한다. 복구 자체가 실패하면 해당 키를 `RECOVERY_REQUIRED`/503으로 격리한다. 이 격리는 현재 프로세스 안에서만 유지된다.
4. 정본 확정 뒤 `afterCommit`의 효과를 실행하고 `deferResponse`에 등록한 HTTP 결과를 전송한다. SSE도 확정 전에는 발행하지 않는다. 기존 요청 ID와 전체 소요 시간, 자원 획득 대기의 `mutationWaitMs` 계측을 유지한다.

04는 이 후보 집합·확정·복구·결과 경계에 영속 journal, 결과 보관 및 재시작 복구를 연결한다. 지금은 프로세스 강제 종료/전원 장애의 다중 파일 원자성, 일반 요청 ID의 중복 방지, 응답 유실 후 결과 확인을 보장하지 않는다. 기존 재구성·AI 요청에 있던 개별 복구나 중복 방지를 일반 저장의 보장으로 확대하지 않는다.

새 알림 생성·댓글 알림 정리·자동 일일 백업은 기존의 부수효과 실패 정책을 유지한다. 원문 확정 뒤 실행하며 오류는 기록한다. 사용자별 알림 RMW 자체는 보호하지만, 이 부수효과의 영속 재시도는 아직 없다. 이동에 포함된 기존 알림 경로 변경은 공동 변경 대상이다.

## 검증 결과

실행 환경·소스 해시·최종 출력 해시는 [검증 기록](validation-02-20261027.json)에 보존한다. 새 시험은 OS 임시 데이터 루트, 독립 포트, 모의 Aion 서버와 없는 작업공간 레지스트리를 사용한다. 저장 barrier와 예약 호출은 시험 프로세스에만 로드하는 `tests/helpers/storage-fs-barrier.mjs`로 제공한다. 운영 API에는 장애 주입 기능을 추가하지 않았다.

출발 커밋을 독립 checkout에서 같은 barrier로 검사하면 댓글 성공 응답 2건 중 파일에는 1건만 남는다. 수정본에서는 같은 문서의 후속 작성·조회가 대기하고, 독립 문서는 처리되며, 성공 2건이 모두 남는다. 기존 진단 원본 result/confirm 파일은 수정하지 않았다. 이는 유실의 재현·해결 근거이며 전체 성능 비교가 아니다.

기존 `test:mcp`는 출발 커밋에서도 공용 연결을 남긴 채 삭제 성공을 기대해 실패했다. 시험에서 공용 연결의 409를 먼저 확인하고 해당 연결을 해제했으며, 모의 보관 API·유휴 상태·이미 삭제한 연결의 200 의미를 기존 삭제 API 시험과 맞췄다. 제품의 공용 연결 보호를 완화하지 않았다. 서버 로그에 보호 문맥 우회 오류가 없어야 한다는 검증도 포함했다.

## 완료 경계

02의 원래 완료 조건은 구현·자체 회귀 검증 범위에서 충족했다. 필수 미완료와 범위 밖 선택 개선은 없다. 03의 필드/read-set 충돌 완화, 04의 journal·재시작·일반 요청 중복 방지, 05의 외부 대기 분리·대기열·취소·재시도 한계, 06의 조회 비용, 07의 독립 통합·전체 성능 비교는 각 담당 업무에 남는다. 웹 전체 소비자 전환과 2MB/5MB/10MB 전체 인수, 운영 배포·실제 Runner 검증은 이번 결과에 포함하지 않는다.
