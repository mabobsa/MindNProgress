## 구현과 읽기 계약

`get_card`는 기존 API의 `readCard` 선택 조회로 필요한 카드와 댓글 페이지·그룹·접근 URL 정보를 한 번에 받는다. `get_document`는 `mcpView`로 기존 full/compact/outline/version 표현을 서버에서 구성한다. `get_card`의 기존 3 HTTP와 `get_document`의 2 HTTP가 각각 1회가 된다. 공유 지식 정리 문맥도 직접 관계·부모/자식·선행 관계에 필요한 카드와 그룹 문맥을 함께 반환한다. 도구 이름·입력 스키마·guide/contextLifecycle은 유지하며 일반 문서 GET의 기본 응답도 유지한다.

서버는 `documentReadStore`의 정규화 원문 안에서 선택하고 반환할 값만 복제한다. 선택 카드에 필요하지 않은 Ref 원본은 읽기 대상에서 제외한다. 필요한 Ref 원본도 대상 카드와 댓글 집계만 복제한다. 댓글은 stat·generation으로 보호한 정렬/카드별/집계 인덱스를 재사용하고 페이지 결과만 반환한다. MCP의 이미지 로컬 경로는 기존처럼 MCP의 dataDirectory를 기준으로 제공한다.

문서 캐시와 댓글 캐시는 각각 64MiB의 유한 LRU다. 원문·정규화·선택 표현의 직렬화 bytes를 함께 계산하며 문서당 선택 표현은 8개 이하로 제한한다. 이는 JS heap/RSS의 64MiB 상한을 뜻하지 않는다. 진행 중 읽기 promise가 끝나도 반환 직전 generation이 바뀌면 다시 읽는다. 사용하지 않는 generation 항목도 제거하고, 모든 외부 반환값은 복제한다.

문서·댓글·Ref 조합은 필요한 문서의 읽기 잠금과 기존 자원 집합 재검증을 사용한다. 그룹 부가 정보는 해당 그룹 설정만 읽기 잠금으로 보호하고 배치 스냅샷을 다시 비교한다. 단일 GET에 전역 catalog 잠금을 추가하지 않는다. 다른 문서의 영구 삭제 barrier 중에도 독립 문서의 선택 조회가 완료된다. 저장·충돌·journal·요청 ID·기한 계약과 원격 미확정 결과 처리는 변경하지 않았다.

캐시에는 권한 판정 결과를 저장하지 않는다. 매 요청의 현재 사용자를 검사하며 문서 정규화의 기존 사용자·수명주기 의존성을 유지한다. 원본·댓글·복원·복구·삭제·시작 migration의 기존 무효화 경계가 문서와 댓글 캐시를 함께 비운다. Ref의 실제 원본·댓글 집계와 현재 그룹 소속이 선택 표현 키에 포함된다. 문서 ETag 형식은 3이며 그룹 소속과 총괄 역할 변경도 반영한다.

위임 GET은 현재 주체와 전체 응답 내용으로 ETag를 만들고 동일하면 304를 반환한다. App은 문서·사용자별 ETag를 보관하고 겹친 요청을 공유하며 조회 중 들어온 변경을 후속 조회한다. 관련 SSE·연결 복구·포커스·화면 재표시 시 갱신하고, 이벤트 유실은 30초 조건부 조회로 보완한다. 오류나 304로 이미 확인한 복구 표시를 지우지 않는다. 200개 완료 이력의 정렬과 결과 본문은 유지한다.

알림 GET은 사용자·권한·서울 날짜·문서/수명주기/사용자 변경 세대가 같으면 완료된 일정 검사와 진행 중 검사를 공유한다. 사용자 항목은 최대 128개다. 일정 검사는 카드의 담당자·기한·상태만 선택하며 기존 알림 생성·중복 제거·읽음 계약을 사용한다. 문서가 바뀌면 다시 검사하고 생성된 알림의 중복을 막는다.

## 측정 조건과 해석

`node scripts/measure-read-cost.mjs <baselineRoot> <candidateRoot> <새 출력 경로>`로 실행했다. 기준 소스는 Git archive, 후보는 담당 변경만 반영한 사본이며 각 프로세스에 같은 격리 계측 preload를 적용했다. Ref 계측은 실행 시 module hook으로 주입하고 소스 파일을 고치지 않는다. 반복 타이머 및 listen 뒤 귀속·lease 복구 작업은 양쪽 모두 중단하고 시작 migration은 유지한다. 초기 측정 run-02에서는 시작 후 귀속 보정이 warm 구간에 섞여 이를 판정 자료에서 제외했으며 원본 로그는 보존한다.

문서 96개 × 카드 20개, 같은 본문 문자열과 순서, 댓글 파일 7개 × 100개, Ref 카드 19개와 원본 5문서, 완료 위임 200개 × 결과 1,000문자를 사용한다. 일정 조건은 없음/담당자·기한 카드 20개를 분리한다. 페이지는 card-1, offset 1, limit 2, desc, 상세 제외다. 각 셀은 새 프로세스에서 cold 1회, warm-up 5회, warm 60회이며 동시 1·10·20으로 실행한다. 기준/후보 순서를 셀마다 번갈아 실행하고 모든 결과의 필요한 내용 해시를 대조한다.

latency는 논리 조회의 HTTP 응답 수신과 내용 비교까지 포함하며 warm-up은 제외한다. CPU는 API 프로세스의 user/system 누적 밀리초로 코어 하나 100% 기준이다. RSS peak는 10ms 표본과 단계 경계의 최대값이다. 응답 bytes는 UTF-8 본문이며 HTTP 헤더·TCP 프레이밍은 제외한다. MCP 모델 실행 시간은 포함하지 않는다. API 호출 묶음은 실제 MCP 구성과 같으며 MCP 자체의 직렬화 비용은 별도의 실제 MCP 회귀로 확인한다.

실제 서버의 파일 읽기·댓글 배열 JSON parse·structuredClone·Ref 확장 진입을 계수한다. `fullDocumentCloneCount`는 fixture 카드 20개 이상의 nodes 배열을 포함한 복제 횟수다. 필드를 줄인 전체 카드 배열도 보수적으로 포함하므로 처리 bytes와 함께 해석한다. 원문이 이미 startup migration 캐시에 있을 수 있어 cold는 프로세스 시작 후 첫 요청이며 OS page cache를 강제로 비우지 않는다. 모든 계측의 CPU/메모리 비용이 포함되고 다른 시스템 작업을 완전히 통제한 실험실 측정은 아니다.

## 남은 비용과 인계

변경된 파일은 다시 parse·정규화해야 하며 캐시가 가득 차면 재조회한다. Ref 표현 키를 만들기 위한 선택 원본 복제·해시, 그룹의 파일 목록/배치 확인, 200개 위임의 상태 조립·정렬·응답 해시는 남는다. 304는 주로 전송량과 UI 처리량을 줄이며 위임의 모든 서버 계산을 제거하지 않는다. 알림은 변경이 있거나 날짜가 바뀌면 전체 일정 대상 문서를 다시 검사한다. 기본 full 문서 조회의 원문 크기를 줄이는 기능은 아니다.

카드 기록 중 명시적 requestId의 결과 조회가 문서 목록을 반환하는 운영 서버/MCP 버전 불일치를 관측했다. 실제 카드가 바뀌지 않았음을 재조회한 후 기존 호출 방식으로 기록했다. 운영 재시작·배포는 수행하지 않았으며 새 MCP와 선택 조회 API는 함께 반영해야 한다.

원래 완료 조건 4개는 자체 구현·검증 기준으로 충족했다. 필수 미완료는 없다. 상위 인수와 07의 독립 통합 검수는 이 자체 완료에 포함하지 않는다. 추가 하위 위임·운영 서버 조작·원격 push·Dooray 변경은 수행하지 않았다.
