# Dooray 대응 제안과 완료 처리

## 전용 대화

- 접수·제안 단계에서는 기존 업무 대화를 재개하지 않는다. 담당 카드와 필요한 기존 대화의 최근 텍스트를 읽기 전용으로 조회한다.
- 새 대화는 메인 머신에서 `server/data/_dooray-response-workspaces/<편집자 ID>/Dooray AI 대응`에 모인다. 실제 데이터 경로는 서버의 데이터 디렉터리 설정을 따른다.
- 임시 렌더링 자료는 `requests/<실행 ID>/` 아래에 분리한다. 공통 폴더는 개발 작업공간이 아니다.
- 서브 머신은 AI 설정에 해당 머신에 미리 만든 제안 전용 폴더의 절대 경로를 입력한다. 메인 머신의 경로를 다른 머신에 복사하거나 추측하지 않는다.
- 같은 요청·같은 담당의 재제안은 전용 대화를 이어 쓴다. 담당이 바뀌면 새 전용 대화를 만들며 이전 전용 대화도 완료 시 보관 대상으로 추적한다.
- 기존 대화·폴더를 자동 이동하거나 삭제하지 않는다. 제안 전용 대화는 카드의 업무 대화 목록에 추가하지 않는다.

## 대응 완료

- 제안 도착·추가 정보 필요·승인 대기·승인 완료·확인 필요 상태에서 사용자가 `대응 완료`를 누른다. 제안 분석이 실행 중인 요청은 먼저 끝나야 한다.
- 완료 시 상단 건수와 미완료 목록에서 제외하고 완료 내역에 제안·출처·담당·완료 시각을 보존한다. Dooray 확인함·업무 상태는 바꾸지 않는다.
- 대응 완료는 실행 승인의 철회가 아니다. 이미 연결된 승인 대화는 완료 후에도 같은 계정·요청 ID·제안 버전·대화 ID로 승인을 검증할 수 있다. 완료 내역에서도 `제안 대화 보기`와 `승인 대화 보기`를 구분해 제공한다.
- 완료된 승인으로 새 대화 시작·새 연결·재승인은 허용하지 않는다. 아직 대화가 연결되지 않았거나, 다른 대화·계정·버전이거나, 제안이 변경된 경우에는 실행 승인 조회를 거부한다.
- 완료 기록을 먼저 저장한 뒤 이 요청이 생성한 전용 대화만 개별 보관한다. AionUi 보관은 프로세스를 중지하므로 유휴 상태와 생성 표식을 검사한다.
- 기존 업무 대화, 다른 계정의 대화, 작업 위치가 바뀐 대화는 자동 보관하지 않는다. 보관 실패 시 완료를 취소하지 않고 완료 내역에 사유와 재시도 버튼을 표시한다.
- 완료한 대화를 AionUi에서 일괄 삭제해도 MnP의 완료 기록은 유지한다. 미완료 대화 삭제는 기존처럼 제안 미시작 상태로 초기화한다.

## 담당 카드로 전달하기

- 담당 경로가 있는 `제안 도착`·`승인 대기`·`승인 완료` 상태에 표시한다. 전달은 대응 완료와 별개이며, 승인 기록이 있어도 이 버튼은 실행이 아닌 재검토를 요청한다.
- 전달 전에 최신 담당 카드를 검증하고 연결된 업무 대화를 선택한다. 기존 대화가 없거나 별도 대화가 필요하면 담당 카드의 일반 AI 대화 시작 화면에서 AI·작업공간을 선택한다.
- 전문에는 Dooray 본문·선택 코멘트 URL과 제안 전체를 포함한다. 담당 AI는 기존 제안을 승인된 계획으로 취급하지 않고 최신 상황에서 독립적으로 재판단해 한국어로 다시 제안한다.
- 이번 전달은 구현·문서 변경·댓글 작성·하위 AI 실행을 승인하지 않는다. 제안 전용 대화의 접수용 JSON 응답 형식도 요구하지 않는다.
- 기존 업무 대화 전송은 같은 제안 회차의 고정 실행 ID로 중복을 막는다. 응답 유실 시 같은 대화의 실행 상태를 확인하며 다른 대화에 우회 전송하지 않는다.
- 전달 접수가 확인되면 `제안 대화 보기`는 해당 담당 카드의 대화를 연다. 기존 완료 기록도 현재 회차의 저장된 전달 대화 ID·머신을 사용한다. 전달 전·실패·응답 미확인·이전 회차의 기록은 사용하지 않고 기존 접수·제안 대화를 연다. 원래 전용 대화의 보관 대상은 바뀌지 않는다.
- 새 업무 대화로 전달할 때도 4,000자 이후의 제안을 자르지 않는다. 전달 한도를 넘으면 전송 전에 오류를 알린다.

## 팝업 높이

데스크톱은 동적 브라우저 높이에서 상하 여백 44px을 뺀 높이를 사용하고, 모바일은 전체 동적 높이를 사용한다. 닫기 버튼은 유지하며 설정·제안 영역이 큰 경우 내용 영역에서 스크롤한다.

## 질문·승인 구분과 새 승인 대화

- AI가 구조화된 `decision`으로 `input`(필수 사실 질문), `approval`(실행 동의), `proposal`(일반 검토 자료)을 반환한다. 승인 대기는 판단 근거와 승인 제목·범위·제외 범위가 모두 있어야 한다. 질문이 섞이면 질문을 우선하며 AI가 승인 완료를 반환할 수는 없다.
- 구버전 답변은 문구로 추측해 전환하지 않는다. `질문·승인 다시 판단`을 누르면 기존 제안을 참고해 새 기준으로 재검토한다. 자동 승인·실행하지 않는다.
- `제안 승인 · AI 대화 시작`을 누르면 로그인한 편집자·시각·제안 버전·본문·범위의 승인 기록을 저장하고 기존 AI 옵션 팝업을 연다. 사용자가 AI·모델·작업공간·MCP 등을 선택한 뒤 시작하면 새 대화에 전달한다. 취소하면 승인 기록은 남지만 대화는 생성하지 않으며 같은 버튼으로 다시 열 수 있다.
- 담당 카드가 없는 신규 구성도 `dooray-response` 용도로 시작한다. 현재 선택한 임의의 카드나 제안 공통 폴더로 귀속하지 않는다. 원문 URL·확보한 본문/댓글·담당 경로 또는 미지정 사유·제안 전문·승인 범위·제외 범위와 수행 절차를 전달한다. 한도를 넘으면 자르지 않고 거부한다.
- 새 AI는 `mindnprogress_get_dooray_response_approval`로 현재 대화에 연결된 서버 승인을 먼저 검증한다. 근거가 없거나 버전·대화가 다르면 실행하지 않는다. 실제 문서 작업 전에 최신 문맥·관련 지침을 확인하며, 그룹 구성 승인을 기능 구현·하위 위임으로 확대하지 않는다.
- 새 대화 연결은 요청의 승인 기록에 저장하며 제안용 보관 대상에서 제외한다. 대화 시작을 작업 완료로 간주하거나 대응 건수에서 자동 제외하지 않는다. 이미 시작한 승인 대화가 있으면 그 대화를 열어 진행한다.
- 담당이 있는 승인 실행은 일반 카드 대화와 동일하게 카드 대화 목록·시작 카드·실행 설정을 연결한 뒤 승인 대화 연결을 확정한다. 시작 카드가 다른 기존 대화로 바꾸는 완료 통보는 거부하며, 같은 완료 통보의 재시도는 문서 버전을 증가시키지 않는다. 담당이 없는 구성 대화에 임의 카드를 귀속하지 않는다.
- 대응 기록의 `제안 대화 보기`는 현재 회차에 실제 전달한 담당 카드 대화를 우선하고, 전달 기록이 없으면 기존 접수·제안 대화를 연다. `승인 대화 보기`는 승인 후 새로 시작해 저장된 실행 대화를 연다. 두 버튼은 같은 위치에서 제공하며, 옵션 창을 취소했거나 아직 승인 대화가 연결되지 않았다면 제안 대화 버튼만 표시한다. 기존 완료 기록에도 저장된 대화 연결을 그대로 사용하므로 별도 데이터 변환이나 재승인이 필요하지 않다.
- 대화 시작 전 제안을 수정하면 이전 승인은 이력으로 남기고 새 제안에는 적용하지 않는다. 승인 기록·이력은 제안 대화 삭제 후에도 보존한다. 오래된 화면의 승인 요청과 타 계정 요청은 거부한다.

## 완료 처리로 승인 검증에 실패했던 대화 이어가기

1. 수정된 API 서버를 적용한다. 개발 화면(4175)을 새로고침하는 것만으로 API 서버(4176) 코드가 갱신되지는 않으므로 서버 실행 방식에 따라 API 재시작도 확인한다.
2. AionUi의 기존 승인 실행 대화를 열거나 Dooray 참조의 완료 내역에서 `승인 대화 보기`를 누른다. 제안 검토용인 `제안 대화 보기`와 혼동하지 않는다.
3. 아래 메시지를 보내 기존 요청 ID·제안 버전과 현재 대화 ID로 승인을 다시 확인하게 한다. 새 승인이나 새 대화를 만들지 않고, 대응 완료 기록을 되돌리거나 승인 검증을 우회하지 않는다.

> 앞선 중단은 Dooray 참조의 ‘대응 완료’를 승인 무효로 처리하던 오류 때문이었습니다. 동일한 요청 ID와 제안 버전으로 서버 승인을 다시 검증해 주세요. 검증에 성공하면 확인된 승인 범위 안에서 작업을 이어가고, 실패하면 변경 없이 중단해 주세요.

## 새 문서의 상위 카드로 승인 작업 인계

- 승인 실행 대화가 문서를 만들어도 현재 대화의 시작 카드와 위임 범위는 바뀌지 않는다. `aiConversationId`를 직접 수정하거나 조회한 카드로 위임 기준을 전환하지 않는다.
- Dooray 참조에서 `새 문서의 상위 카드에서 이어가기`를 누르고 활성 문서의 원본 루트를 선택한다. 서버가 원본 Dooray URL, 최초 제안·승인 범위·제외 범위와 이전 실행 대화의 사용자·AI 텍스트 전문을 시간순으로 준비한다. 내부 도구 원시 출력과 인증 정보는 제외하고 실제 산출물은 최신 카드에서 재검증한다. 대화 조회 실패·페이지 누락·크기 초과는 임의 요약이나 잘라내기 없이 차단한다.
- 사용자가 대상·전문·기존 승인 범위를 확인하면 인계 기록만 저장하고 기존 `AI 대화 시작` 팝업을 연다. 대화나 대상 문서가 확인 도중 바뀌면 다시 검토해야 한다. 옵션 취소 시 새 대화는 실행하지 않으며 `준비한 인계 대화 시작`으로 이어간다. Dooray 참조 팝업은 유지한다.
- 새 대화는 선택한 루트에서 정식으로 시작하고 기존 상하위 위임 규칙을 그대로 적용한다. 인계 자체는 새 실행 범위의 승인이 아니다. 후속 승인 발언은 메시지 ID가 포함된 실제 사용자 메시지와 계획을 대조하며 불명확하면 재승인 대기로 마친다.
- 최초 `승인 대화 보기`를 보존하고 별도의 `인계 대화 보기 · 문서명`을 제공한다. 이미 대응 완료한 기록도 연결된 승인이 유효하면 인계할 수 있다. 서버 승인은 최초 대화와 실제 연결된 인계 대화에서만 확인할 수 있다.

## AionCore 작업공간 응답 계약과 누락된 위임 대화 복구

- AionCore의 작업공간 응답은 `workspaceId`, `jobId`, `leaseId`, `projectRoot` 네 필드를 제공한다. 네 값은 필수이며 일치해야 한다. 응답에 없는 `branch` 때문에 정상 배정을 거부하지 않되, 브랜치가 명시되어 다르면 거부한다. 실제 Git 브랜치·HEAD·세션 소유권 검증은 유지한다.
- 2026-09-11에 응답 필드 밖의 브랜치 비교로 정상 실행이 격리된 사례가 있었다. 대화는 생성됐지만 MnP의 대상 대화 연결이 저장되지 않았으므로 새 위임을 만들면 안 된다.
- 기존 상위 카드 AI 또는 로그인한 사용자의 명시적 복구 요청에서만 저장된 operation을 조회하고, 실제 대화·작업공간·시작 카드·Git 상태가 일치하면 누락된 연결을 복구한다. 작업공간 점유 ID와 대화를 재사용하며 기존 분석 결과·카드 상태는 유지한다. 다른 소유권, 브랜치, HEAD, 진행 중 Git 작업이나 활성 대화가 있으면 중단한다.
- AionCore는 종료된 operation을 생성 시각 기준 1시간이 지나면 후속 실행 접수 때 정리한다. 대화는 남아도 operation 조회는 404가 될 수 있다. 이 경우 미연결된 신규 위임에 한해 불변 시작 카드 기록으로 후보를 한정하고, 최초 사용자 위임 전문의 지시 SHA-256·저장 지시·문서/카드/편집자·배정 정보·생성 시각·실제 대화 경로를 교차 검증한다. 전체 메시지 페이지를 확인하지 못하거나 일치하는 대화가 없거나 여럿이면 복구하지 않는다.
- 만료 대응에서도 상위 카드 권한, 유휴 대화, 실제 Git·세션 소유권 검증은 동일하다. 만료 기록을 새로 만들거나 완료 상태를 추측하지 않으며, 검증에 사용한 최초 메시지 ID와 해시만 감사 기록에 보존한다. 인증 정보를 포함할 수 있는 원본 전문은 재전송하거나 저장하지 않는다.
- 분석이 이미 완료됐다면 분석을 반복하지 않고 무변경 확인과 완료 보고 등 누락된 절차만 지시한다. 상태 조회나 서버 재시작만으로 격리 해제·AI 재실행·완료 판정을 하지 않는다.

## 승인·인계 대화의 작업공간 기본값

- 일반 카드 대화 옵션은 유지한다. Dooray 승인·인계에서는 MnP 서버 디렉토리를 업무 구분 없이 기본값으로 넣지 않는다.
- 담당 카드, 문서 루트, 문서 내 연결 대화 순으로 같은 실행 머신의 작업공간을 참고한다. 등록된 pool의 경로는 현재 registry의 integration 경로를 기본값 후보로 사용하며 worker를 임의 배정하지 않는다. 후보가 하나면 자동 입력하고, 없거나 여러 개면 등록 경로와 MnP 경로를 선택지로 보여 준다.
- 기본값은 제안일 뿐이다. 사용자는 입력·폴더 탐색·최근 경로 선택으로 언제든 바꿀 수 있고 MnP 유지보수 문서의 MnP 경로도 허용한다. 서버는 확인한 경로와 실제 실행·생성된 대화의 경로가 같은지 검사하며 프로젝트 자체를 Holdem으로 강제하지 않는다.
- 잘못 시작한 과거 대화의 실제 작업 디렉토리는 소급 변경하지 않는다. 기존 실행 결과를 확인하고 상위 카드 인계에서 올바른 경로를 선택하여 새 대화를 시작한다.
