# 기존 문서의 부분 저장

`PATCH /api/maps/{mapId}/content-patch`는 기존 문서의 변경된 카드·관계만 받습니다. 브라우저 자동저장과 MCP 카드 추가·수정·본문 부분 수정·이동·삭제·지식선 변경은 이 경로를 사용합니다. 2,000,000바이트 요청 제한은 유지하며, 변경하지 않은 `description`과 `sharedKnowledge`를 요청에 다시 싣지 않습니다.

요청에는 현재 `baseVersion`과 `patch`를 보냅니다. `patch`의 `nodeAdds`는 새 카드 전체, `nodeChanges`는 기존 카드에서 바뀐 최상위 필드(`set`·`remove`)와 `data` 필드(`dataSet`·`dataRemove`)만 담습니다. `nodeDeletes`는 삭제 ID입니다. 관계는 `edgeUpserts`·`edgeDeletes`로 변경하고, `nodeOrder`·`edgeOrder`에는 적용 뒤의 전체 ID 순서를 넣습니다. 서버는 현재 원문에 변경분을 적용하고 권한·버전·형식·공유 지식 메타데이터·진행률 집계·이력·백업·알림을 기존 저장 경로에서 처리합니다.

새 `preconditions`가 없는 기존 요청은 버전이 다르면 `409 VERSION_CONFLICT`와 최신 문서를 반환합니다. 새 계약은 카드 존재·종류·Ref와 변경 필드의 이전 값 해시를 검사하여 독립 변경을 최신 문서에 적용합니다. 관계·계층·순서·삭제 등 구조 변경은 엄격한 문서 버전 조건을 유지합니다. 충돌을 받으면 원래 기대값을 최신 값으로 자동 교체하지 말고 충돌 대상을 검토한 뒤 새 의도를 결정합니다. 변경 요청이 실패해도 전체 문서 `PUT`으로 우회하지 않습니다. 잘못된 patch는 `400 MAP_CONTENT_PATCH_INVALID`, 요청 자체가 2MB를 넘으면 기존처럼 413입니다. 입력과 오류 계약은 [REQ-MNP-03 구현 문서](api-storage/implementation-03.md)를 따릅니다.

성공 응답은 기존 소비자의 기준선 갱신을 위해 아직 전체 문서와 요약을 반환합니다. 기존 `PUT /api/maps/{mapId}`도 유지되지만 기존 문서의 전체 교체에는 `baseVersion`·`baseLifecycleVersion`이 필수이며, 2MB 초과 문서를 보내면 여전히 413입니다. 명시적 사용자 덮어쓰기인 레거시 `force=true`는 별도 경로로 유지하며 자동 충돌 우회에 사용하지 않습니다. 신규 클라이언트는 부분 저장 경로를 사용해야 합니다.

새 카드의 본문과 실제로 수정한 기존 카드의 본문은 변경 요청에 포함됩니다. 따라서 작은 카드·관계·위치·본문 수정은 문서 전체 크기와 무관하게 저장할 수 있지만, **한 번에 변경한 내용 자체**가 2MB를 넘으면 413 제한이 그대로 적용됩니다. 이 경로는 요청 크기를 줄이는 조치이며, 성공 응답과 명시적 문서 조회의 전체 문서 반환까지 축소하지는 않습니다.
