# MindNProgress·Dooray 작업 절차

전역 지침에는 불변조건만 있다. 이 문서는 그 불변조건을 **어떻게 지키는지**와 각 필드의 역할 구분을 담는다.

**MindNProgress MCP 서버가 이미 알려주는 것은 여기 적지 않는다** — `get_context` 선행 확인, `update_card`의 부분 병합 동작, 변경 후 재조회, `waitingItems` 처리, 댓글과 `sharedKnowledge`의 기본 역할. 그건 MCP 도구 설명과 `get_context`·`read_me_first` 응답의 `guide`(특히 `guide.sharedKnowledgePolicy`, `guide.commentRules`, `guide.operationRules`)에서 읽는다. 아래는 MCP가 알려주지 않는 내용과 MCP 연결 전에도 지켜야 하는 텍스트 안전 불변조건만이다.

## MindNProgress 카드 작업 규칙

### 카드 저장 안전 규칙 (필수)

`update_card`의 부분 병합 동작(변경할 필드만 전달, 생략 필드·위치 보존, 빈 문자열·빈 배열은 명시적 초기화, 완료 시 `waitingItems` 자동 해제, Ref 카드 원본 동기화)은 **MCP 도구 설명과 `get_context` 제품 규칙에 있으므로 여기서 반복하지 않는다.** 아래는 MCP가 알려주지 않는 에이전트 행동 규칙으로, 기존 카드 본문을 옮겨 적다가 `sharedKnowledge` 92줄을 손상시킨 실제 사고에서 나왔다.

- **한국어 자연어는 실제 문자로 작성한다.** 기존 한글 본문을 `\uXXXX` 유니코드 이스케이프나 코드포인트 조립으로 생성하거나 옮겨 적지 않는다.
- **기존 `description`·`sharedKnowledge`의 일부를 고칠 때는 `mindnprogress_patch_card_text`가 기본 경로다.** 필드 전체를 다시 생성해 `update_card`로 보내지 않는다.
  1. `mindnprogress_get_card`로 대상 필드의 `card.textIntegrity.sha256`을 받아 `expectedSha256`으로 넘긴다.
  2. `operation`은 `replace_once`(`find`가 원문에서 정확히 한 번 일치), `replace_between`(유일한 `startMarker`·`endMarker` 사이 교체, 두 경계는 보존), `append` 중 하나다. 바꿀 부분과 짧은 경계 문자열만 보내므로 긴 본문을 옮겨 적지 않는다.
  3. 같은 필드에 여러 번 고칠 때는 병렬로 보내지 않고, 직전 응답의 `after.sha256`을 다음 `expectedSha256`으로 쓴다.
- **저장 후에는 원문과 문자열 비교로 검증한다.** 수정 전 원문을 파일로 확보해 두고, 저장 후 다시 조회한 값과 프로그램으로 비교해 의도한 부분만 바뀌었는지 확인한다. 길이가 같아도 내용이 다를 수 있으므로 눈대중이나 길이 확인으로 끝내지 않는다. `find`·`replace`에 넣은 비ASCII 문자열은 저장된 값에서 글자 단위로 다시 대조한다.
- 승인된 정리처럼 필드 전체를 다시 써야 할 때만 `update_card`로 전체 값을 보낸다. 이때도 원문을 파일로 확보해 버전·해시를 확인하고 저장 후 같은 방식으로 대조한다.
- **섹션 단위로 교체할 때는 뒤에 오는 섹션이 잘리지 않았는지 확인한다.** 특정 헤딩 이후를 잘라 붙이면 그 뒤 섹션이 조용히 사라진다.
- **문서 단위 복원(`mindnprogress_restore_history`)은 마지막 수단이다.** 다른 세션이 그 사이에 편집했다면 그 작업까지 되돌아간다. `mindnprogress_list_history`로 사고 시점 이후의 편집자와 시각을 먼저 확인하고, 가능하면 해당 카드의 해당 필드만 다시 저장해 고친다.
- **손상시켰다면 복구 후 전체 카드를 사고 전 스냅샷과 대조**해 내가 바꾼 카드·필드만 달라졌는지 확인하고, 다른 세션의 변경을 덮어쓰지 않았는지 보고한다.

### 업무 설명

- `description`은 업무의 배경, 요청, 목적, 범위, 요구사항과 완료 조건을 기록하는 영역이다.
- 진행 과정, 시행착오와 작업 일지는 업무 설명에 기록하지 않는다.
- 요구사항의 변경이 확인되면 기존 내용과 모순되지 않도록 반영한다.
- 요구사항이 불명확하거나 기존 내용과 충돌하면 임의로 수정하지 말고 사용자에게 확인한다.

### 공유 지식

- 작성·갱신 조건(`writeWhen`), 남길 것과 뺄 것(`keep`·`exclude`), 통합·보존(`update`·`preserve`), 이력 위치(`history`), 용량 부족 처리(`capacity`), 15,000자 기준(`length`)의 원문은 서버 `guide.sharedKnowledgePolicy`에 있다. MnP 작업에서는 그 원문을 따르고 여기서 다시 적지 않는다.
- 서버 응답을 읽기 전에도 지킬 요지: `sharedKnowledge`는 수행 보고가 아니라 **다른 카드·후속 담당자의 판단·구현·사용에 필요한 현재 유효한 지식의 최신본**이며, 작업·검증을 했다는 사실만으로 추가하지 않고 **새 지식이 없으면 변경하지 않는다.**
- 서버 원문에 더해 지킨다.
  - 누가 어떤 판단이나 행동에 사용할지 설명할 수 있는 결론만 남긴다.
  - 필요한 수치·해시가 실제 소비 조건이면 그 조건과 함께 보존한다. 지식선으로 이 카드를 소비하는 카드가 의존하는 조건도 보존한다.
  - 해시 조건부 부분 수정은 위 「카드 저장 안전 규칙」의 `mindnprogress_patch_card_text` 절차를 쓴다. 전체 재작성 뒤에는 저장 결과를 다시 조회해 원문과 대조한다.
  - 용량이 부족해도 불가 보고만 하고 멈추지 않는다. 서버 `capacity` 절차대로 기존 절에 통합할 수 있는지부터 판단한다.

### 댓글

- MnP 카드 댓글의 기록 시점, `summary`(머리말로 시작하는 240자 이하 1~2문장)와 `detail`(최대 6,000자) 구분, 상세 작성 조건, 생략 대상, 등록 전 최근 댓글 확인은 서버 `guide.commentRules`·`guide.operationRules`와 `mindnprogress_manage_comment` 설명을 따른다. 구조화 보고 본문은 `summary`가 아니라 `detail`에 넣는다.
- 머리말의 뜻은 MnP와 Dooray에서 같다.
  - `[진행]`: 수행한 작업, 현재 상태와 다음 단계
  - `[차단]`: 진행할 수 없는 원인과 필요한 정보 또는 결정
  - `[결과]`: 완료 내용, 검증 결과와 산출물 링크
- Dooray 댓글은 `summary`·`detail` 구분이 없는 단일 본문이다. 1행에 AI 작성 표기(아래 「AI 작성 Dooray 업무·댓글 표기 규칙」), 머리말을 쓰는 경우 그다음 줄에 머리말과 요약, 이어서 상세 순으로 쓴다. 표기보다 머리말을 먼저 두지 않는다.
- 댓글 작성이나 업무 완료가 공유 지식 갱신 의무를 뜻하지 않는다. 위의 새 지식·변경 조건을 만족할 때만 `sharedKnowledge`를 갱신한다.

### Dooray 기록

- 내용이 길거나 표, 첨부파일, PPTX, 검토 이력 또는 여러 조직의 공유가 필요하면 Dooray 업무를 상세 원문의 저장 위치로 고려한다.
- 연결된 Dooray 업무가 있으면 새 업무를 중복 생성하지 않고 기존 업무를 우선 사용한다.
- 새로운 Dooray 업무가 필요하면 대상 프로젝트와 등록할 내용을 사용자에게 먼저 제안한다.
- 사용자가 승인했거나 현재 요청에 Dooray 등록이 명시된 경우에만 업무를 생성하거나 수정한다.
- Dooray에 상세 내용을 기록한 경우 MindNProgress에는 핵심 요약과 Dooray 링크를 기록한다.
- 이미지는 `dooray_project_upload_attachment`로 해당 업무에 업로드하고, 반환된 `fileId`를 `![이미지 설명](/files/{fileId})`로 본문·댓글 또는 마크다운 표의 셀에 넣는다.
- 새 업무는 생성 → 이미지 업로드 → 본문 수정 순서로 처리한다. 댓글 이미지도 해당 업무에 업로드하며, 댓글은 `text/x-markdown`으로 작성한다.
- 기존 첨부는 `dooray_project_get_post`의 `files`에서 ID를 확인해 재사용한다. 업로드 경로와 허용 루트는 도구 설명을 따른다.
- **Dooray 본문 수정은 전체 교체다.** `dooray_project_update_post`의 `body`는 지정하면 기존 본문 전체를 교체하고, `dooray_project_update_post_comment`의 `content`도 전체 교체다. 부분 수정 도구나 해시 조건 저장, MnP 같은 이력 복원 도구가 없다.
  1. 기존 본문에 덧붙일 진행·결과는 본문을 고치지 말고 댓글로 남기는 것을 우선한다.
  2. 본문을 고쳐야 하면 `dooray_project_get_post`로 원문을 받아 파일로 보존하고, 바꿀 범위를 최소화한다. 사람이 쓴 본문의 바꾸지 않을 부분은 원문 그대로 둔다.
  3. 저장 직전에 다시 조회해 그사이 다른 사람이 바꾸지 않았는지 원문 파일과 비교한다. 달라졌으면 저장하지 않고 다시 시작한다.
  4. 저장 후 다시 조회해 원문 파일과 프로그램으로 비교하고, 의도한 부분만 바뀌었는지와 비ASCII 문자열을 글자 단위로 확인한다. 손상이 확인되면 보존한 원문으로 즉시 되돌리고 사용자에게 보고한다.
  - 담당자·참조자 목록 인자(`to_member_ids`, `cc_member_ids`)도 지정하면 전체 교체이므로 바꿀 의도가 없으면 넘기지 않는다.

### 상태 관리

- 카드 상태와 진행률은 실제 작업 결과에 맞게 갱신한다.
- 차단된 업무는 원인과 해제에 필요한 조건을 댓글로 기록한다.
- **실제 하위 업무가 있는 문서 Root와 일반 `isWork=false` 묶음 카드의 `progress`·`status`는 서버가 계산하는 읽기 전용 파생값이다.**
  이 카드들의 `progress`·`status`를 직접 수정하거나 `mindnprogress_update_card`의 변경 데이터에 포함하지 않는다.
- 진행률을 변경할 때는 자동 집계의 원본이 되는 실제 `isWork=true` 업무만 갱신한다.
  - 체크리스트가 있는 업무는 체크리스트 항목의 완료 여부를 갱신하고 서버가 계산한 진행률·상태를 확인한다.
  - 체크리스트가 없는 업무는 실제 결과에 맞춰 해당 업무의 `progress`·`status`를 갱신한다.
- 자동 집계 결과가 예상과 다르면 최신 문서를 다시 조회해 계층 관계, `isWork`, Ref 여부, 실제 업무의 진행률과 체크리스트를 확인한다.
  집계 원본이 정상인데도 결과가 다르면 파생값을 직접 덮어쓰지 말고 서버 계산 문제로 보고한다.
- 이번 작업으로 집계 원본이 변경되어 Root 진행률이 달라졌다면 최종 응답에 이전 값, 변경된 값과 변경 사유를 포함한다.
- 연결된 Dooray 업무의 진행 상태는 사용자가 명시적으로 요청한 경우에만 변경한다. Dooray에는 진행률 필드가 없으므로 여기서 진행 상태는 워크플로 상태 변경(`dooray_project_set_post_workflow`)과 완료 처리(`dooray_project_set_post_done`)를 뜻한다. MnP 카드를 완료로 바꿨다는 이유로 Dooray 업무를 함께 완료 처리하지 않는다.

### 완료 및 보고

- 작업 완료 후 카드의 업무 설명, 공유 지식, 댓글, 상태와 진행률이 서로 모순되지 않는지 확인한다.
- 최종 응답에는 다음 항목을 구분하여 알린다.
  - 수정한 카드
  - 추가한 댓글
  - 변경한 공유 지식
  - 변경한 상태와 진행률
  - 생성하거나 수정한 외부 업무 및 문서
- 그룹 흐름의 위임 회신·인계 보고는 `mnp-spec-driven-development`의 구조화 보고 키에 위 항목을 대응시켜 한 번만 적는다. 목록을 따로 한 번 더 적지 않는다.

## AI 작성 Dooray 업무·댓글 표기 규칙

- **AI가 Dooray 업무를 생성(등록)하거나 댓글을 작성할 때는 각 내용의 첫 줄에 대상에 맞는 AI 작성 표기를 넣는다.**

  업무 본문:

  ```
  > **※ 본 업무 내용은 AI가 작성했습니다.** (AI: {AI 종류} / 모델: `{모델 ID}` / 사고 강도: `{사고 강도}`)
  ```

  댓글:

  ```
  > **※ 본 코멘트 내용은 AI가 작성했습니다.** (AI: {AI 종류} / 모델: `{모델 ID}` / 사고 강도: `{사고 강도}`)
  ```

  - `{AI 종류}`에는 현재 사용 중인 CLI 이름을 넣는다 (예: Claude Code, Codex CLI). 이 글을 실제로 쓰는 에이전트의 시스템 프롬프트가 밝히는 제품 이름을 쓰며, 그 CLI를 띄운 실행 계층(AionUi, Claude Agent SDK, ACP, MindNProgress)은 AI 종류로 쓰지 않는다. MnP 기록의 AI 귀속은 서버가 `get_context`에서 확인하므로 이 표기와 별개이며, 외부 MCP 세션이 `get_context`에 `aiType`을 넘길 때도 같은 이름을 쓴다.
  - 표기는 본문·댓글의 1행이다. 댓글 머리말(`[진행]` 등)이나 제목·요약은 그다음 줄에 둔다.
  - 기존 업무 본문 또는 댓글을 AI가 전면 재작성하는 경우에도 대상에 맞는 표기를 적용한다.
  - 사람이 작성한 업무 본문 또는 댓글에 부분 수정만 하는 경우에는 표기를 새로 붙이지 않는다.
  - 모델과 사고 강도는 아래 방법으로 **실제 값을 조회해 기록**하고, 추측으로 채우지 않는다.

### 모델·사고 강도 확인 방법

- AionUi 연동 세션은 MindNProgress에서 시작됐는지와 관계없이 **현재 실행 중인 AionUi 대화**를 우선 조회한다. 카드에 연결된 대표 대화는 현재 작성 중인 AI 대화와 다를 수 있으므로 1차 출처로 사용하지 않는다.
- `AIONUI_HELPER_BIN`과 `AIONUI_CONVERSATION_ID`가 있으면 다음 절차를 사용한다.
  1. 현재 대화 ID는 `AIONUI_CONVERSATION_ID`를 사용한다.
  2. `{"path":"/api/conversations/{현재 대화 ID}/runtime-config","reason":"Dooray AI 작성 표기용 현재 모델과 사고 강도 확인"}` JSON을 `AIONUI_HELPER_BIN diagnose http get`의 표준 입력으로 전달한다.
  3. `AIONUI_RUNTIME_TOKEN`을 명령이나 출력에 직접 넣지 않는다. helper가 주입된 인증 정보를 사용한다.
- 위 런타임 환경이 없거나 helper 조회가 실패하고, 현재 작업에 MindNProgress `get_context` 결과가 이미 있다면 그때만 보조 경로를 사용한다.
  1. `conversationId`: `selection.card.data.aiConversationId`
  2. AionUi 주소: MindNProgress `/api/health`의 `aionUiWebBaseUrl`
  3. `GET {AionUi 주소}/api/conversations/{conversationId}/runtime-config`
- 일반 대화에서 런타임 환경을 찾지 못했다는 이유로 MindNProgress 문서나 카드를 새로 탐색하지 않는다. 런타임 1회와 이미 확보된 MindNProgress 보조 경로로도 확인할 수 없으면 탐색을 중단하고 확인된 항목만 사용한다.
- 모델은 `data.model.value`, 사고 강도는 `data.thought_level.value`를 사용한다.
- **`data.model.value`가 버전 없는 별칭(예: `opus`, `sonnet`)이면** 현재 실행 중인 에이전트의 시스템 프롬프트나 런타임이 정확한 모델 ID(예: `claude-opus-5-5`)를 명시한 경우 그 ID를 기록한다. 정확한 ID를 확인할 수 없으면 별칭을 그대로 기록하고 버전을 추측해 붙이지 않는다. 두 값이 서로 다른 모델 계열을 가리키면 시스템 프롬프트의 값을 쓴다.
- **subagent·워크플로가 띄운 하위 에이전트**는 부모 프로세스의 `AIONUI_CONVERSATION_ID`·`AIONUI_HELPER_BIN`을 물려받으므로, 위 절차로 조회한 값은 부모 대화의 모델·사고 강도다. 하위 에이전트로 실행 중이면(시스템 프롬프트가 subagent·하위 실행임을 밝히거나 Task·Agent 도구·워크플로로 시작된 경우) 위 AionUi 조회값을 자기 값으로 쓰지 않는다. 모델은 자기 시스템 프롬프트가 명시한 ID를 쓰고, 사고 강도는 자기 시스템이나 런타임이 명시한 경우에만 적고 아니면 생략한다.
- 각 필드의 `source`가 `runtime` 또는 `snapshot`이면 유효하며, `has_active_runtime: false`여도 스냅샷은 사용할 수 있다.
- AionUi 밖에서 실행된 세션은 시스템이나 런타임이 명시적으로 제공한 값만 사용한다. CLI 이름이나 일반 지식만으로 모델과 사고 강도를 추정하지 않는다. CLI 설정 파일(`~/.claude/settings.json`의 `model`·`effortLevel`, `~/.codex/config.toml`의 `model`·`model_reasoning_effort` 등)은 프로필·명령줄로 덮어쓸 수 있어 실행값이 아니므로 이 출처로 쓰지 않는다.
- 값이 없거나 조회로 확인할 수 없으면 해당 항목을 생략하고 추측하지 않는다. 표기 괄호에는 확인된 항목만 `/`로 연결하며, AI 종류만 확인됐다면 `(AI: {AI 종류})`로 기록한다.
