# 위임과 검수 게이트

## 역할 분리

역할 이름과 역할별 담당은 [SKILL.md 「용어」](../SKILL.md#용어)의 역할 표(총괄 담당자·문서 담당자·상위 담당자·하위 실행자·독립 검수자·수신 담당자)를 따른다.

### 상하위 카드 실행 경계

이 절은 수행 주체 규칙의 단일 기준이다. SKILL.md 「권한과 확인」과 공통 문서 운영의 「수행 주체 유지」 항목은 이 절을 요약한다.


- 현재 수행자가 루트·상위·묶음 카드를 담당하고 승인된 구현이 기존 하위 업무 카드에 속하면, 해당 카드에 `mindnprogress_delegate_ai_work`로 위임한다. 하위 카드가 있다는 사실을 알면서 상위 담당자가 직접 구현하는 수행 주체 변경은 허용하지 않는다.
- 특정 하위 카드의 구현 실행 승인은 그 카드에 필요한 위임까지 포함한다. 위임은 선택 가능한 추가 작업이 아니므로 사용자가 직접 수행과 위임 중 하나를 별도로 정하게 하지 않는다. 분석·검토·제안 승인만 있는 경우에는 위임하지 않는다.
- 상위 담당자는 하위 업무의 코드·에셋 변경, 테스트·Play, 커밋과 진행률·완료 결과를 실행자 대신 수행하거나 기록하지 않는다. 승인된 카드 계약·Ref 준비, 위임 상태 확인과 결과 검수는 계속 담당한다.
- 새 하위 카드 생성·범위 재배정은 해당 변경까지 포함한 승인 범위에서 수행한다. 기존 승인에 포함되지 않은 새 카드 생성, 범위 확대, 다른 문서 소유 업무 또는 예상 밖의 외부 작업은 실행 전에 승인받는다.
- 사용자가 상위 담당자의 직접 수행을 명시적으로 요청한 경우에만 수행 주체 예외를 적용한다.

한 수행자가 여러 역할을 수행할 수는 있지만, 이를 상위 카드 역할에서 하위 업무를 직접 실행하는 근거로 사용하지 않는다. 독립 검수 단계에서는 자신의 이전 요약이나 완료 보고를 근거로 사용하지 않는다.

검수 대화를 고를 때 MindNProgress의 대화 선택 정책은 이전 판단을 이어가는 연속 검수에 관련 기존 검수 대화를 우선한다. 누락 복구 감사와 최종 제품 검수는 이전 완료 판정을 신뢰하지 않고 원본에서 다시 시작하므로 정책의 '의도적인 별도 관점 검수'로 보고 새 대화를 선택하며, 그 근거를 `decisionReason`에 적는다.

총괄→문서 루트 전달은 `mindnprogress_send_group_document_instruction`, 문서 내부의 실제 하위 업무 실행은 `mindnprogress_delegate_ai_work`를 사용한다. 전자의 전달·응답 상태를 후자의 실행 완료로 해석하지 않는다.

그룹의 역할별 준비·재사용·승인 확인은 [공통 문서 운영](common-document-workflow.md)을 따른다. 역할 배정이나 이 절차 자체는 실행 권한이 아니다.

## 작업 결과 보고와 인수

위임 결과 회신과 카드·문서·세션 간 작업 인계에 적용한다. 이 보고는 후속 담당자가 상태·근거·다음 행동을 정확하게 판단할 수 있도록 작성한다.

### 목적과 기본 형식

- 보고는 수신자의 판단 정확성, 근거 추적성, 문맥·조회 비용을 기준으로 구성한다. 짧은 분량이나 사람에게 읽기 좋은 문장을 우선 목표로 삼지 않는다.
- 위임·작업공간·체크포인트처럼 기존 전송 규격이 구조화해 기록하는 값은 그 필드를 우선 사용한다. 별도 규격이 없는 보고 본문은 YAML·JSON 등 명시적인 키·값 구조를 기본으로 한다. 키는 아래 영문 키를 쓰고, 설명이 필요한 값의 자연어는 한국어로 쓴다.
- MindNProgress 위임 회신은 실행 대화의 최종 답변이 상위 담당자에게 전달되고 사용자가 보는 대화에도 남는다. 전달 한도와 절단은 아래 「MindNProgress 전달 경로와 한도」를 따른다. 최종 답변을 이 구조로 작성하고, 다른 지침이 요구하는 최종 응답 항목(예: `mnp-dooray`의 카드·댓글·공유 지식·상태 변경, 작업공간 규칙의 변경 파일·커밋·작업 트리 상태)은 아래 키에 대응시켜 한 번만 적는다.
- MindNProgress가 위임 전문에 붙이는 결과 지시(맡은 목표·달성 결과·검증 근거부터, 필수 미완료와 범위 밖 선택 개선 구분)는 이 키 구조와 함께 지킨다. 목표는 `context`, 달성 결과는 `status`, 검증 근거는 `checks`·`evidence`, 필수 미완료는 `next.required`, 선택 개선은 `next.optional`에 대응하며, 최종 답변에서는 `context` 다음에 `status`와 `checks`를 먼저 둔다.
- 카드 댓글로 남길 때는 `summary`에 `mnp-dooray`가 정한 머리말과 1~2문장 판정을, `detail`에 이 구조를 쓴다. 길이 한도(작성 시점 서버 기준 `summary` 240자, `detail` 6,000자)는 도구 스키마가 우선한다. 한도를 넘으면 상세를 여러 댓글로 나누지 않고, 판정·필수 미완료·제약은 `detail`에 남긴 채 상세 이력을 커밋·산출물 참조로 바꾼다. Dooray 댓글은 `mnp-dooray`가 정한 순서(1행 AI 작성 표기, 다음 줄 머리말)로 시작하고 본문에 이 구조를 사용한다.
- 사람용 요약은 선택 사항이다. 요청이나 설명 필요에 따라 구조화된 보고에서 파생해 제공하며, 별도의 판정이나 근거를 만들지 않는다.
- 정보를 줄일 때는 중복과 상세 이력의 반복을 줄인다. 승인 범위, 완료 조건, 검증 한계, 미해결 사항과 후속 작업의 제약은 보존한다.

### 보고 정보

다음 정보를 구분한다. 아래 키를 기본으로 사용하되, 기존 전송 규격에 대응 필드가 있으면 재사용한다.

- `context`: 보고 대상, 실제 작업·지시 식별자, 승인 범위, 기준 버전·커밋.
- `changes`: 이번 변경과 이전 유효 보고 이후 달라진 사실. 변경 파일, 결과 커밋 또는 무변경 확인, 작업 트리 상태와 카드·댓글·공유 지식·상태·진행률·외부 업무의 기록 변경을 포함한다.
- `status`: 판정 대상별 현재 상태와 그 판정의 적용 범위. 담당 요구사항은 ID별로 구현 수준·검증 상태·차단 상태를 [요구사항 추적 규칙](requirement-traceability.md)의 상태 분류로 적는다.
- `checks`: 검증 대상, 결과, 검증자(역할과 수행 주체 식별자), 확인 방법, 적용 버전·조건, 근거 참조.
- `next`: 두 하위 키로 나눈다. 해당 항목이 없으면 `없음`으로 적는다.
  - `required`: 원래 완료 조건의 필수 미완료, 남은 게이트, 다음 담당자·행동·재개 조건, 후속 작업에서 보존할 제약.
  - `optional`: 범위 밖 선택 개선 제안. 상위 담당자의 실행 지시나 새 완료 조건이 아니다.
- `evidence`: 원본 결과, 로그, 이미지, diff, manifest 등의 참조 위치와 식별 정보.

- 필드 이름과 값의 의미를 일관되게 유지한다. 개수·순번·식별자·측정값은 각각 구분하고, 측정값에는 필요한 단위와 조건을 붙인다.
- 누락이나 `null`을 성공·0건·해당 없음으로 해석하지 않는다. 판단에 필요한 값이 미확인이라면 명시하고, 기존 시스템 필드의 의미는 해당 규격을 따른다.
- 현재 보고만으로 판정 범위와 다음 행동을 식별할 수 있게 한다. 변경점만 보내는 보고는 기준 보고를 명시하고 수신자가 참조할 수 있을 때 사용한다.

### 판정과 근거

- 판정 대상은 요구사항 ID, 실행 종료, 통합, 보고 전달·수신과 아래 「카드 완료, 더미 완료와 제품 완료」의 업무 카드·더미 구현·외부 연동·문서·제품으로 구분한다. 각 상태를 해당 대상에 연결하고, 한 대상의 완료를 다른 대상의 완료로 승계하지 않는다.
- 통합은 하위 실행자가 판정하지 않는다. MindNProgress는 명시적 체크포인트만 통합 작업공간(main)에 반영하며, 반영 방식에 따라 통합 후 커밋 SHA가 worker 커밋 SHA와 다를 수 있다. 하위 실행자는 `changes`에 체크포인트·worker 커밋을 통합 전 식별자로 적고, 상위 담당자가 위임 상태와 통합 작업공간에서 통합 여부와 통합 후 커밋을 확인해 재전달 보고의 `context`·`evidence`에 적는다.
- 실행자의 보고, 수신자의 자료 검수, 별도 검수자의 실제 재실행을 구분한다. 각 검증 기록에 누가 무엇을 확인했는지 남기고, 상위 담당자의 검수 기록을 추가할 때도 원래 실행자와 근거를 보존한다.
- 검증 통과·실패·미실행·확인 불가·해당 없음을 구분한다. 이 값은 개별 검증의 결과이며, 요구사항의 검증 상태로 집계할 때는 [요구사항 추적 규칙의 상태 표](requirement-traceability.md#상태-분류)의 대응을 따른다. 완료 판정을 제한하는 미검증 범위와 외부 조건은 근거 자료에만 숨기지 않고 `status`·`checks`·`next`에 명시한다.
- 상세 로그, 전체 해시 목록과 과거 이력은 기존 원본·산출물을 참조한다. 참조는 대상과 버전이 식별되어야 하며, 재현·후속 작업에 필요한 정확한 식별자는 보존한다.
- 해시 일치는 자료의 동일성 근거로 사용한다. 요구사항 충족 여부는 해당 구현·검증 근거와 연결해 판정한다.
- 원본 근거를 보존하고 실제 참조 위치를 확인한 뒤 중복 본문을 줄인다. 접근할 수 없는 근거는 접근 불가로 표시하고, 해당 근거를 검수한 것으로 기록하지 않는다.
- 참조는 수신자가 접근할 수 있고 작업공간 해제 후에도 유지되는 위치(통합된 커밋, 프로젝트가 정한 공용 증거 폴더, MindNProgress 카드 댓글, 승인 범위 안의 Dooray 업무 첨부, 원본 일치가 확인된 기존 공용 산출물 등)를 사용한다. 증거 파일은 저장소에 커밋하지 않는다. worker 작업공간의 로컬 경로만으로 근거를 보고하지 않으며, `knowledge-inbox`·`review-artifacts`는 근거 보관 위치로 사용하지 않는다.
- 작업공간 로컬 로그처럼 영속 위치에 없는 텍스트 근거는 판정에 필요한 핵심 발췌와 생성 조건을 본문에 남긴다. 캡처 이미지처럼 발췌할 수 없는 근거를 영속 위치에 둘 수 없으면 접근 불가 근거로 보고하고, 수신자는 이를 검수한 것으로 기록하지 않는다.

### 인수와 재전달

- 수신 담당자는 원래 작업 계약과 보고의 대상·범위·기준 버전을 대조한다. 완료 판정과 다음 행동을 바꾸는 주장에는 필요한 원본 근거를 확인한다.
- 모호한 약어·수량·순번을 문맥으로 확정하지 않는다. 원자료로 해소하고, 해소할 수 없으면 해당 판단을 미확정으로 유지한다.
- 보고 수신, 근거 검수와 결과 인수를 구분한다. 요구되는 검수 게이트가 충족된 범위만 인수한다. MindNProgress 기록과의 대응은 아래 표를 따른다.
- `next.optional`의 선택 개선을 새 요구사항·완료 조건이나 자동 재위임 대상으로 채택하지 않는다. 채택하려면 승인 범위 안인지 확인하고, 범위 밖이면 사용자에게 제안한다.
- 상위로 재전달할 때는 현재 상태, 자신이 추가로 확인한 내용, 남은 조건과 다음 행동을 기록하고 하위 원본 결과를 연결한다. 하위의 상세 감사 이력을 반복 복사하거나 자신의 검증으로 바꾸어 쓰지 않는다.

| 이 지침의 단계 | MindNProgress 기록 | 의미하지 않는 것 |
|---|---|---|
| 실행 종료·통합 | 위임 상태가 보고 대기(`waiting-parent` 등)로 바뀐다. 하위 실행과 체크포인트 통합이 끝난 결과만 수신 확인할 수 있다. | 요구사항·업무 카드 완료 |
| 보고 수신 | 상위 담당자가 `mindnprogress_list_ai_delegations(includeResult=true, 대상 카드 필터)`로 원문과 `resultHash`를 읽고 `mindnprogress_refresh_ai_delegation`의 `acknowledgeResultHash`로 확인하거나, 결과가 상위 재개 턴에 전달될 때 서버가 자동 기록한다(`reportReceipt.method`가 `parent-acknowledged` 또는 `dispatch-delivered`). 어느 쪽이든 위임 `state`는 `completed`가 된다. 조회만으로는 수신 확인이 되지 않는다. 이미 수신이 기록됐으면 다시 확인하지 않는다. | 근거 검수, 결과 인수, 후속 실행 승인 |
| 근거 검수 | 서버 상태 필드가 없다. 상위 담당자가 원래 계약과 원본 근거를 대조하고 검수 결과를 카드 댓글 등에 남긴다. | 결과 인수 |
| 결과 인수 | 검수 게이트를 충족한 범위만 카드 상태·추적표에 반영하고 상위로 재전달한다. | 문서·제품 완료 |

### MindNProgress 전달 경로와 한도

- **위임 결과 캡처**: 서버는 하위 실행 대화의 마지막 답변 메시지(`text` 또는 `tips`) 하나를 결과로 저장한다. 작성 시점(2026-10-21) 구현은 12,000자를 넘으면 앞 12,000자와 `[MindNProgress 결과 절단]` 표시만 저장하고, `resultHash`도 표시를 포함한 저장 값으로 계산하므로 잘려도 수신 확인은 통과한다. 위임 결과는 최대 100,000자의 원문을 따로 보관한다. 한도 값과 표시 방식은 서버가 바꿀 수 있으므로 서버 응답과 도구 설명을 우선한다.
  - 하위 실행자는 최종 답변을 한 메시지로 작성하고, 판정(`context`·`status`·`checks`·`next.required`)을 앞에 둔다. 한도를 넘을 수 있는 상세는 영속 위치에 두고 참조로 적는다. 보고 뒤에 짧은 메시지를 덧붙이면 앞의 보고는 결과로 저장되지 않으므로 최종 보고는 턴의 마지막 텍스트 메시지 하나에 담는다.
  - 수신 담당자는 결과 조회 응답에 절단 여부·원문 길이 메타데이터가 있으면 확인한다. 작성 시점 구현의 `mindnprogress_list_ai_delegations` 필드는 `resultTruncated`·`resultOriginalLength`·`resultSplitSuspected`이고, 잘린 결과는 `includeResult=true`와 `includeFullResult=true`로 보관 원문(`resultFull`)을 읽는다. 수신 확인의 `acknowledgeResultHash`에는 `resultFullHash`가 아니라 `resultHash`를 쓴다. 메타데이터가 없는데 결과가 한도 근처 길이이거나 문장 중간에 끝나면 절단 가능성을 미확인으로 다루고, 하위 카드 댓글·커밋 등 원본에서 빠진 판정을 확인한다.
- **그룹 지시 회신**: 문서 담당자는 지시 전문의 「완료 보고 라우팅」 블록에 따라 회신 대상을 정하고, 완료 보고에 `instructionId`를 포함한다. 서버는 지시를 받은 첫 응답 턴의 마지막 메시지만 `replied`로 기록하고 총괄을 재개하지 않으므로, 최종 완료 보고는 첫 턴에서 끝난 경우를 포함해 `session-message`로 유효 회신 대상 대화에 한 번 직접 보낸다. 이 전송은 사용자가 승인한 지시에 포함된 회신 요청이므로 `session-message`의 명시적 요청에 해당한다. 이때 첫 줄에 `instructionId`를 적고 접수·대기·중간 보고는 보내지 않는다. 회신 대상을 확인할 수 없으면 다른 세션에 임의로 전송하지 않고 현재 대화의 최종 답변으로 보고하며 회신 대상 미확인을 표시한다. 회신 대상 대화가 다른 머신의 AionUi에 있어 `target_not_found` 등으로 전송이 실패하면 재시도하지 않고, 최종 보고를 문서 루트 카드의 `[결과]` 댓글로 남긴 뒤 실패 사실과 함께 현재 대화의 응답으로 사용자에게 알린다. 총괄 담당자는 `replied`를 최종 완료 보고 수신으로 해석하지 않고, `mindnprogress_list_group_document_instructions(includeContent=true)`의 응답 원문과 대상 문서의 실제 카드·위임 결과를 확인한다.

## 구현 카드 최소 계약

구현을 위임하기 전에 카드에 다음이 있어야 한다.

- 현재 단계와 그 단계에 배정된 담당 요구사항 ID 전체
- 이번 단계 완료 후 확인할 수 있는 결과, 구현 범위와 후속 단계로 남기는 범위
- 변경 소유 파일·화면·Prefab 또는 공통 계약
- 실제로 재사용할 기존 구현·근거 Ref
- 정책·데이터·UI별 검증 방법
- 독립적으로 판정 가능한 완료 조건
- 외부 전달물과 재개 조건

복수의 결과가 있으면 결과 중심 체크리스트를 사용한다. 별도 하위 카드의 작업을 체크리스트에 중복하지 않는다.

MindNProgress 안내는 결과 중심 체크리스트가 빠졌으면 하위 실행자가 작업 전에 작성하게 한다. 이 흐름에서 그 체크리스트는 카드에 이미 있는 담당 요구사항 ID와 완료 조건을 나눠 적는 용도로만 쓴다. 하위 실행자는 새 완료 조건을 만들거나 기준을 바꾸지 않으며, 요구사항 ID나 완료 조건 자체가 없으면 체크리스트로 채우지 않고 위임 계약 누락으로 보고한다.

처리 규칙이 다른 유형이 섞인 대량 항목(예: 출처·처리 정책이 다른 수천 건의 문자열·데이터)은 한 위임에 묶지 않는다. 유형별로 나누고, 유형마다 표본을 먼저 처리·검증한 뒤 범위를 넓힌다. 한 유형에 정한 판단 규칙을 다른 유형에 일괄 적용하지 않는다.

## 위임·지시 전문 작성

하위 업무 위임 전문과 그룹 문서 지시의 `instruction`은 수신자가 추측 없이 범위와 기준을 해석할 수 있어야 한다.

- 첫머리에 현재 단계, 목표 한 문장, 담당 요구사항 ID, 이번 위임 후 사용자가 새로 확인할 수 있는 동작을 적는다.
- 완료 조건과 제외 범위를 목록으로 적는다.
- 정의하지 않은 약어, 내부 라운드 번호, 카드 별칭을 쓰지 않는다. 처음 쓰는 약어는 정의하고, ID·해시·경로는 백틱으로 분리하며 해시는 무엇의 해시인지 적는다.
- 사용자 승인은 도구의 승인 근거 필드와 서버가 확인한 범위로 전달한다. 상위 담당자가 확인하지 않은 승인을 본문에서 단정하지 않는다.
- 긴 배경·이력은 원본 카드·Ref·커밋으로 연결하고 본문에 반복 복사하지 않는다.
- 이 스킬의 이름·접근 경로, 담당 역할과 먼저 읽을 실제 Ref는 아래 「정책 지식 연결」에 따라 명시한다.

## 정책 지식 연결

- 하위 카드가 UI를 제작·변경하거나 시각 검수하면 시안 정합 원칙 지식 카드를 `source → target`, `reuse-first`로 연결한다.
- 더미 데이터·저장·서버 경계 등 별도 정책이 실제 구현 판단을 바꾸면 해당 정책 Ref도 연결한다.
- 관련 가능성만 있는 카드를 무조건 연결하지 않는다.
- 위임 전문에 지식 카드의 핵심 내용을 다시 복사하기보다, 먼저 읽고 적용할 대상과 완료 조건을 명시한다.
- 문서 담당자가 쓸 Ref는 루트에 연결하고, 하위 실행자에게 필요한 Ref는 실제 업무 카드에도 직접 연결한다. 루트 지식의 자동 상속을 가정하지 않는다.
- 위임 전문에 이 스킬의 이름·접근 경로, 담당 역할과 먼저 읽을 실제 Ref를 명시한다. 수신 담당자는 시작 시 원본 내용을 읽고 적용할 규칙·완료 조건을 확인하며, 필수 자료를 읽지 못하면 해당 실행을 보류한다.
- 저장 후 source, target과 policy를 재조회한다.

## 실행 순서

1. 분석 카드와 구현 감사를 완료하고, 문서별로 결과와 완료 조건이 명확한 단계를 정한다.
2. 현재 단계에 필요한 최소 공통 계약을 통합한다.
3. 현재 단계의 구현 카드를 실행한다. 소유권과 선행 조건이 분리된 같은 단계 업무만 병렬화한다.
4. 그 단계의 통합, 필요한 자동·Play 검증과 결과 인수를 마친다.
5. 완료 근거와 후속 업무를 확인한 뒤 승인된 다음 단계로 이동한다. 다음 단계의 이미 승인된 실행을 다시 승인받지 않는다.
6. 최종 문서·제품 검수에서 해당 범위의 원본 요구사항 전체를 독립 감사한다.

공통 계약 문서 전체가 끝날 때까지 모든 작업을 막지 않는다. 하위 기능이 사용할 최소 계약과 소유권이 확정되면 해당 단계의 구현을 시작한다. 외부 의존 업무를 분리해도 실제 선행 전달물이 생기는 것은 아니므로, 그 전달물이 필요한 단계의 대기는 유지한다.

## 카드 완료, 더미 완료와 제품 완료

완료 판정 대상을 구분한다.

- **업무 카드 완료**: 카드에 명시된 담당 범위와 완료 조건을 모두 구현하고 필요한 자동·Play 검증을 통과했다.
- **더미 구현 완료**: 결정적 Fixture/Provider와 더미 에셋으로 해당 카드가 맡은 사용자 흐름, 상태, 오류·재시도와 복귀를 검증했다.
- **외부 연동 완료**: 실제 서버 계약과 최종 리소스로 교체하고 필요한 회귀 검증을 통과했다.
- **문서 완료**: 문서가 소유한 필수 업무 카드가 모두 완료되고 미분류·미검증 요구사항과 미완료 외부 연동이 없다.
- **제품 완료**: 최신 원본 전체의 요구사항과 문서 간 통합 흐름을 독립 검수하고 남은 필수 업무가 없다.

더미 구현 카드의 담당 범위가 더미 구현과 검증으로 명시됐다면 해당 카드만 `done`으로 처리할 수 있다. 이를 외부 연동이나 문서·제품 완료로 보고하지 않는다.

실제 서버·최종 리소스·정책 결정이 필요한 후속 작업은 별도의 `isWork=true` 업무 카드로 유지한다. 필요한 전달물과 재개 조건을 `waitingItems`에 기록하고, 대기가 해소되어 구현·검증이 끝나기 전에는 `done`으로 처리하지 않는다. 아직 시작하지 않았으면 `planned`, 일부 작업 후 차단됐다면 `in-progress`를 유지한다.

### 외부 의존 업무 분리

현재 카드에서 수행·검증할 수 있는 범위는 끝났고 외부 전달물에 의존하는 작업만 남았다면, 다음 순서로 후속 업무를 분리하고 현재 카드를 완료할 수 있다.

1. 남은 일이 실제 서버·최종 리소스·정책 결정·다른 소유자의 전달물에 의존하는지 확인한다. 현재 범위의 구현 결함이나 수행 가능한 필수 검증을 외부 대기로 바꾸지 않는다. 새 카드 생성과 범위 재배정이 승인돼 있는지도 확인한다.
2. 같은 업무의 후속 카드가 있으면 재사용하고, 없으면 승인 범위 안에서 생성한다. 원래 요구사항 ID, 남은 구현·검증 조건, 소유자, 필요한 전달물, 재개 조건과 원카드 링크를 기록한다. 실제 대기는 후속 카드의 `waitingItems`에 남기고, 같은 문서의 선행 카드 의존성은 `blockedBy`에 기록한다.
3. 후속 카드의 저장 결과를 재조회해 미완료 업무와 대기 조건이 보존됐는지 확인한다. 저장 실패·미확인이면 원카드의 범위·체크리스트·대기를 그대로 두고 완료하지 않는다.
4. 원카드의 남은 범위가 구현·검증됐는지 근거로 확인한 뒤, 이동한 항목·후속 링크를 남기고 계약·체크리스트·대기·요구사항 소유권을 정리한다. 원래 요구사항과 필수 완료 조건은 삭제하지 않고 담당 카드만 재배정한다. 체크리스트 정리만으로도 `done/100`이 될 수 있으므로 이 변경도 완료 저장으로 취급한다.
5. 해당 카드 담당 실행자가 확인된 범위의 완료를 기록하고, 저장 후 양쪽 카드의 상태·대기·연결을 재조회한다. 상위 담당자는 분리와 인수의 정합성을 확인하며 실행자 대신 작업 결과를 만들지 않는다.

이 절차는 더미 구현뿐 아니라 외부 의존 부분을 독립적으로 분리할 수 있는 업무에 적용한다. 내부 범위의 필수 검증이 남거나 실패했으면 현재 카드를 완료하지 않는다. 후속 카드가 미완료인 동안 원래 요구사항의 최종 완료와 문서·제품 완료도 미완료로 유지한다.

### 상태와 진행률 저장

`status=done` 또는 `progress=100`을 적용하면 서버가 `waitingItems`를 해제한다. 대기가 남은 카드를 완료로 만들지 않는다. 하위 업무가 있는 묶음·루트 카드의 진행률과 상태는 실제 업무 카드에서 자동 집계하므로 직접 설정하지 않는다.

체크리스트가 비어 있지 않은 카드는 서버가 체크 비율로 `progress`와 `status`를 계산하며, 이 값이 함께 보낸 `status`보다 우선한다. 모든 항목을 체크하면 같은 저장에서 `done/100`이 되고 `waitingItems`도 해제된다. `waitingItems` 자체는 상태와 진행률을 바꾸지 않는다. 외부 대기가 남은 카드에서는 대기 해소 후에만 판정할 수 있는 항목(예: 실제 서버 계약 반영 후 회귀 검증)을 미완료로 남기고, 대기 대상 작업을 완료로 체크하지 않는다. 저장 후 `status`와 `waitingItems`를 재조회하고, 의도와 달리 완료·해제됐으면 해당 체크를 되돌린 뒤 대기 항목을 다시 등록한다.

단계 전체가 끝날 때까지 진행률을 고정하지 않는다. 하위 실행자는 실제 완료가 확인된 체크리스트와 검증 상태를 그때 반영하고, 상위 담당자는 이를 검수·인수한다. 단계 완료 조건은 다음 단계로 넘어가는 기준이며 진행 사실을 숨기는 기준이 아니다.

- diff와 변경 범위
- 컴파일·정적 오류
- 파일·Prefab 소유권 위반
- 공통 계약 우회 또는 중복 모델
- 플랫폼·프로젝트 규칙
- 더미 경계와 최종 교체 가능성

### 요구사항 전수 검수

단계 검수의 대상은 그 단계에 배정된 원본 요구사항 전체와 변경 영향 범위다. 최종 문서·제품 검수와 누락 복구 감사에서는 해당 문서·제품의 원본 요구사항 전체를 확인한다. 개별 위임이 끝날 때마다 관련 없는 전체 문서를 다시 검수하지 않는다.

- 판정 대상 범위에 해당하는 최신 원본의 각 요구사항 ID
- 현재 코드와 Prefab의 실제 구현
- 자동 테스트 이름과 실제 결과
- 실제 Play 재현과 결과
- 부분 구현·외부 차단·정책 결정 대기 분류
- 삭제된 과거 동작의 잔존 여부

판정 대상 범위에서 두 검수 모두 통과해야 한다. 하위 실행자가 바꾼 diff만 정상이라고 전체 요구사항을 완료 처리하지 않는다.

이미 검수·인수한 범위는 완료 근거와 적용 버전을 유지한다. 요구사항 변경, 실제 결함 발견, 공통 계약·구현 변경의 영향이 있을 때 해당 카드·검증을 재개하며 근거를 적는다. 새 위임·후속 카드 생성이나 표현 보완만으로 완료 카드를 다시 열지 않는다. 최종 전수 검수는 유지하되 발견한 문제의 영향 범위만 재개한다.

## UI Play·시안 대조

UI 카드에는 최소 다음 증거를 남긴다.

- 사용한 최신 버전 시안 위치
- 실제 진입 경로와 준비 데이터
- 확인한 선택·비선택·잠김·빈 상태·오류·팝업
- 대상 해상도와 Safe Area 조건
- 시안과 다른 부분, 수정 결과 또는 미해소 사유
- 최종 리소스 교체 지점

과거 버전의 캡처와 Play 결과는 회귀 후보일 뿐 최신 버전 증거로 자동 승계하지 않는다.

## 완료 판정

### 업무 카드 완료

`isWork=true` 업무 카드는 다음 조건을 모두 만족할 때만 `done`으로 처리한다.

- 카드에 명시된 담당 범위와 완료 조건을 모두 충족했다.
- 요구되는 자동 검증과 Play 검증을 수행하고 실제 결과를 기록했다.
- 부분 구현, 미확인 결과와 교체 예정 임시값을 완료로 포함하지 않았다.
- 해당 카드가 직접 기다리는 외부 전달물이나 결정이 없다.
- 별도 후속 카드가 필요한 작업은 생성하고 소유자·완료 조건·재개 조건을 기록했다.

더미 업무 카드와 외부 연동 카드의 완료 구분은 위 「카드 완료, 더미 완료와 제품 완료」를 따른다.

### 문서 완료

다음 중 하나라도 남으면 문서 전체 완료가 아니다.

- 소유 문서가 없는 요구사항
- 근거 없는 구현 완료
- 완료로 집계된 부분 구현
- 완료로 오인된 더미 구현
- 검증 방법이 필요한데 결과가 없는 요구사항
- 미완료 외부 연동 카드
- 재개 조건 없는 외부 차단
- 지식 연결이 필요한 UI 카드의 누락
- 최신 원본과 대조하지 않은 기존 완료 카드
- 미분류·미검증 요구사항

문서 루트와 중간 묶음의 완료 상태는 서버의 하위 업무 집계 결과를 사용한다. 자동 집계값을 문서 완료 선언에 맞추기 위해 직접 덮어쓰지 않는다.

### 제품 완료

모든 문서가 완료된 뒤에도 최신 원본 전체, 문서 간 계약, 실제 통합 흐름과 최종 리소스를 독립 검수한다. 문서별 완료 보고를 단순 합산해 제품 완료로 선언하지 않는다.

최종 검증을 종료하기 전에 총괄 원장과 총괄 문서의 추적·집계 카드에 하위 결과가 되돌려 기록됐는지 확인한다. 반영되지 않은 위임 결과, 하위 결과가 있는데 0%로 남은 추적 카드, 소유 문서가 없는 `isWork=true` 카드를 점검한다. 이 점검은 현재 서버가 강제하지 않으므로 [회귀 평가의 자동화 후보](regression-evaluation.md#자동화-후보)를 수동으로 적용한다.

독립 검수 결과가 기존 완료 보고와 다르면 과거 기록은 보존하고 현재 추적표와 영향 업무 카드의 상태를 정정한다.
